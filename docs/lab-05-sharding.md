# 1. Выбор данных для шардирования

### 1. Какую сущность вы выбрали?

**Бронирования — таблица `bookings`.** Это единственная таблица сервиса, растущая
без ограничений: 5 000 005 строк против 50 000 пользователей, 2 000 мероприятий
и 200 площадок. Она же выбиралась scaling entity в ЛР1–4. Справочники маленькие
и остаются на primary целиком.

### 2. Какое поле используется как shard key?

**`user_id`.** Все бронирования одного пользователя лежат на одном шарде.

### 3. Почему выбран именно этот ключ?

Хороший shard key должен иметь высокую кардинальность и присутствовать
в основных запросах. Проверены четыре кандидата:

| Кандидат | Значений | Что будет | Вывод |
|---|---|---|---|
| **`user_id`** | **50 000** | запросы пользователя идут в один шард; все его брони — одна локальная транзакция | **выбран** |
| `event_id` | 2 000 | старт продаж на популярный концерт — это все записи в **один** шард именно в пиковый момент (hotspot); «мои бронирования» превращаются в запрос ко всем шардам | нет |
| `id` бронирования | 5 млн | идеальный баланс, но ни один запрос пользователя его не знает заранее — каждый список становится scatter-gather | нет |
| `created_at` | — | диапазонное шардирование по времени: все новые записи идут в последний шард, остальные простаивают | нет |

Решающий аргумент — **локальность**. Пользователь смотрит свои бронирования,
оформляет новые и получает статистику, и всё это касается только его строк.
При `user_id` в качестве ключа каждая такая операция обходится одним сервером.

### 4. Насколько равномерно он будет распределять данные?

**По пользователям — идеально** в пределах хэш-функции: 50 000 значений против
3–4 шардов. **По бронированиям — почти так же хорошо**, потому что у пользователей
близкий объём:

```
бронирований на пользователя: min 61, медиана 100, p99 124, max 155
```

Самый активный пользователь — 155 бронирований из 5 млн, то есть 0.003 %.
Ни один пользователь не может перегрузить шард в одиночку. Замер это подтвердил:
при `hash % 3` худшее отклонение от идеала — **0.56 %** (задание 4).

Оговорка: данные сгенерированы, активность равномерная. В реальном сервисе
бывают «киты» — например, корпоративный аккаунт, который бронирует тысячи мест.
Все его строки лежат на одном шарде, и этот шард станет горячим. Лечится
отдельным обращением с такими ключами (см. вопрос 10).

### 5. Какие запросы сервиса используют этот ключ?

| Запрос | shard key есть? | Сколько шардов |
|---|---|---|
| `GET /api/users/{id}/bookings` — мои бронирования | да | **1** |
| `GET /api/users/{id}/stats` — моя статистика | да | **1** |
| `POST /api/bookings` — оформить бронь (`user_id` в теле) | да | **1** |
| `GET /api/bookings/{id}` — бронь по id | нет (если id не кодирует номер шарда) | **все** |
| `GET /api/events/{id}/bookings` — брони мероприятия | нет | **все** |
| `GET /api/bookings?status=&from_date=` — список для администратора | нет | **все** |
| `GET /api/bookings/stats/revenue` — выручка | нет | **все** + агрегация в приложении |

Пользовательские запросы — один шард. Административные и аналитические — все
шарды. Это цена выбора: аналитику при шардировании обычно выносят в отдельное
хранилище или на реплики, собранные из шардов.

Добавлены 4 сервиса в [`docker-compose.yml`](../docker-compose.yml): три рабочих


Бэкенду шарды передаются одной переменной:

```yaml
SHARDS: "shard-0=postgresql://...@shard-0:5432/booking_shard,shard-1=...,shard-2=...,shard-3=..."
SHARD_ROUTER_NODES: ""       # какие из них в router'е; пусто — все
SHARD_STRATEGY: consistent   # consistent | modulo
SHARD_VNODES: "100"
```

## Это действительно независимые серверы

```
shard-0: 16.15, system_identifier=7686926115681554470, база booking_shard
shard-1: 16.15, system_identifier=7686926114774855718, база booking_shard
shard-2: 16.15, system_identifier=7686926113940316198, база booking_shard
shard-3: 16.15, system_identifier=7686926116733243430, база booking_shard
```

`system_identifier` у всех четырёх разный: это четыре отдельных кластера.
У реплики из ЛР4 он совпадает с primary — там одна база в двух копиях,
здесь четыре разных базы.

## Схема шарда

```
                         Table "public.bookings"
   Column    |           Type           | Nullable | Default
-------------+--------------------------+----------+---------
 id          | bigint                   | not null |
 user_id     | integer                  | not null |
 event_id    | integer                  | not null |
 status      | character varying(20)    | not null |
 seats_count | integer                  | not null |
 total_price | double precision         | not null |
 created_at  | timestamp with time zone | not null | now()
 updated_at  | timestamp with time zone |          |
Indexes:
    "bookings_pkey" PRIMARY KEY, btree (id)
    "ix_bookings_user_id_created_at" btree (user_id, created_at DESC)
```

Два решения, которые потребовало шардирование:

- **Внешних ключей нет.** Пользователи и мероприятия живут на primary, а PostgreSQL
  не умеет ссылаться на таблицу другого сервера. Существование пользователя
  и мероприятия проверяет приложение перед записью.
- **`id` выдаёт общая последовательность на primary.** Если бы у каждого шарда
  была своя, одинаковые `id` появились бы на разных шардах. Альтернативы — UUID
  или id со встроенным номером шарда (Snowflake). Такой id решил бы заодно проблему
  поиска по id без shard key.

## Бэкенд видит все шарды

`GET /api/shards` до загрузки данных:


# 3. Реализация простого Router

[`app/sharding/router.py`](../app/sharding/router.py):

```python
def stable_hash(value) -> int:
    digest = hashlib.md5(str(value).encode("utf-8")).digest()
    return int.from_bytes(digest[:4], "big")          # 0 … 2^32-1


class ModuloRouter:
    def __init__(self, nodes: list[str]):
        self.nodes = list(nodes)

    def shard_for(self, key) -> str:
        return self.nodes[stable_hash(key) % len(self.nodes)]
```

## Почему не встроенный `hash()` Python

Это первое, что приходит в голову, и оба его варианта здесь ломаются:

- **для строк `hash()` случаен в каждом процессе** (`PYTHONHASHSEED`). Два воркера
  uvicorn, или один и тот же бэкенд до и после перезапуска, отправили бы пользователя
  на разные шарды — и его бронирования «потерялись» бы;
- **для чисел `hash(101) == 101`**, то есть хэша нет вовсе. Шард определялся бы
  остатком от самого `user_id`: последовательные id раскладывались бы по кругу,
  а любая закономерность в id превращалась бы в перекос.

Router обязан давать один и тот же ответ в любом процессе и в любой момент.
MD5 выбран не ради криптографии, а ради стабильности и равномерности.

## Пример работы

```
hash(101) =  951316472    951316472 % 3 = 2  → shard-2
hash(102) = 3968423523   3968423523 % 3 = 0  → shard-0
hash(103) = 1769262682   1769262682 % 3 = 1  → shard-1
```

## Router внутри сервиса

API [`/api/shards/...`](../app/routers/shards.py) выбирает шард router'ом.
Выбранный шард видно в заголовках ответа:

| Endpoint | Что делает | Заголовки |
|---|---|---|
| `GET /api/shards` | конфигурация и распределение | — |
| `GET /api/shards/route/{user_id}` | куда router отправит пользователя, по обеим стратегиям | — |
| `GET /api/shards/users/{user_id}/bookings` | бронирования пользователя | `X-Shard`, `X-Shards-Queried: 1` |
| `POST /api/shards/bookings` | создать бронирование | `X-Shard` |
| `GET /api/shards/bookings/{id}` | бронь по id — scatter-gather | `X-Shards-Queried: 4` |
| `GET /api/shards/bookings/{id}?user_id=…` | то же с shard key | `X-Shards-Queried: 1` |

Создание бронирования через API:

```
HTTP/1.1 201 Created
x-shard: shard-1
{"shard": "shard-1", "id": 5000006, "user_id": 101, "event_id": 5,
 "status": "confirmed", "seats_count": 2, "total_price": 8005.92, ...}
```

Бронирование физически лежит только на одном шарде:

```
shard-0: 0    shard-1: 1    shard-2: 0    shard-3: 0
```

Поиск той же брони:

```
GET /api/shards/bookings/5000006              → x-shards-queried: 4, x-shard: shard-1
GET /api/shards/bookings/5000006?user_id=101  → x-shards-queried: 1, x-shard: shard-1
```

Без shard key router не знает, где искать, и опрашивает все шарды. С ним — один.

**Application-level join.** В ответе «мои бронирования» есть название мероприятия,
хотя бронирования лежат на шарде, а мероприятия — на primary. SQL-запросом через
два сервера это соединить нельзя. Приложение делает два запроса и склеивает
результат само:

```python
rows   = shard.execute("SELECT ... FROM bookings WHERE user_id = :u ...")
titles = primary.execute("SELECT id, title FROM events WHERE id = ANY(:ids)")
```

# 4. Распределение данных

## Как загружались данные

[`scripts/lab05/load.py`](../scripts/lab05/load.py) читает **все 5 000 005 реальных
бронирований** с primary одним потоком `COPY ... TO STDOUT`. Каждая строка
уходит в шард, выбранный router'ом по её `user_id`, и пишется туда пачками
через `COPY ... FROM STDIN`. После загрузки число строк сверяется с primary.

```
router: modulo, шарды: shard-0, shard-1, shard-2
загружено 5 000 005 бронирований за 44.6 с (на primary 5 000 005)
```

## Результат: `hash(user_id) % 3`

| Шард | Пользователей | Бронирований | Доля | От идеала | Размер |
|---|---|---|---|---|---|
| shard-0 | 16 667 | **1 666 092** | 33.32 % | −0.03 % | 236 MB |
| shard-1 | 16 586 | **1 657 842** | 33.16 % | −0.53 % | 234 MB |
| shard-2 | 16 747 | **1 676 071** | 33.52 % | +0.56 % | 236 MB |
| shard-3 | — | 0 | — | не в router | 16 kB |
| **итого** | **50 000** | **5 000 005** | | | |

Идеально на шард: 1 666 668. max/min = **1.011**, наибольшее отклонение — **0.56 %**.

## Выводы

**Насколько равномерно распределились данные?** Почти идеально. Разница между самым
большим и самым маленьким шардом — 18 229 строк, 1.1 %. Это обычный статистический
разброс: 50 000 ключей, случайно разложенных по трём корзинам.

**Есть ли заметный дисбаланс?** Нет. Отклонения меньше процента в обе стороны.

**Может ли такой дисбаланс стать проблемой?** Такой — нет, полпроцента не ощутит
ни диск, ни процессор. Проблемой становится дисбаланс **другого происхождения**,
которого равномерность хэша не видит:

- **перекос по объёму данных** — пользователь-«кит» с тысячами броней целиком
  на одном шарде;
- **перекос по нагрузке** — строк поровну, но на одном шарде оказались самые
  активные пользователи;
- **перекос из-за стратегии** — задание 6 показывает, что базовое кольцо даёт
  одному шарду 45 % данных.

Шард в кластере работает как самое слабое звено: система начинает тормозить,
когда перегружен **хотя бы один** шард, даже если остальные простаивают.

# 5. Что произойдёт при добавлении нового shard?

## Расчёт

`hash(key) % 3` → `hash(key) % 4`. Запись останется на месте, только если
`h % 3 == h % 4`. Оба остатка определяются остатком `h % 12`, и совпадают они
только при `h % 12 ∈ {0, 1, 2}`. Это **3 случая из 12**, значит, на месте останется
25 %, а переедет **75 %**.

## Результат на данных сервиса

Перенос выполнен **физически**
([`scripts/lab05/rebalance.py`](../scripts/lab05/rebalance.py)):
данные реально переехали между серверами, а затем проверено, что каждый
пользователь лежит там, куда его отправляет новый router.

```
Всего записей:    5 000 005 бронирований (50 000 пользователей)
Новый shard:      shard-3

Изменили shard:   3 749 262 бронирований  (74.99 %)   37 477 пользователей (74.95 %)
Не изменили:      1 250 743 бронирований  (25.01 %)

перенос занял 52.7 с
проверка: пользователей не на своём шарде — 0; бронирований до 5 000 005, после 5 000 005
```

Куда переехали бронирования (строка — откуда, столбец — куда):

|  | → shard-0 | → shard-1 | → shard-2 | → shard-3 |
|---|---|---|---|---|
| **shard-0** | · | **415 431** | **418 589** | 415 826 |
| **shard-1** | **420 208** | · | **414 755** | 406 491 |
| **shard-2** | **410 251** | **427 151** | · | 420 560 |

Распределение после переноса — снова идеальное:

| Шард | Бронирований | Доля | От идеала | Размер |
|---|---|---|---|---|
| shard-0 | 1 246 705 | 24.93 % | −0.26 % | **355 MB** |
| shard-1 | 1 258 970 | 25.18 % | +0.72 % | **356 MB** |
| shard-2 | 1 251 453 | 25.03 % | +0.12 % | **357 MB** |
| shard-3 | 1 242 877 | 24.86 % | −0.57 % | 177 MB |

## Вывод: почему добавление одного PostgreSQL двигает так много данных?

**Потому что N входит в формулу для каждого ключа.** `h % 3` и `h % 4` — разные
функции, и при смене N пересчитывается адрес **каждой** записи. Совпадают они
только случайно, в 1/4 случаев.

Самое показательное — матрица выше. Новому шарду нужна четверть данных,
около 1.25 млн строк. А переехало **3.75 млн**: **2.5 млн строк переехали между
старыми шардами**, которые никто не трогал. Например, 415 431 бронирование
перешло с shard-0 на shard-1, хотя оба шарда были и остались в кластере.
Это чистые потери: трафик, нагрузка на диски и окно, в котором данные
лежат не там, где их ищет router.

Нагрузка растёт с объёмом данных. У нас это 52.7 секунды на одной машине;
у реального кластера на терабайты — часы или дни массового переноса.

**Побочный эффект — раздувание таблиц.** Старые шарды выросли с 236 до 355 MB,
хотя строк в них стало меньше: 1.67 млн → 1.25 млн. Каждый шард одновременно
отдавал строки и принимал чужие. Место удалённых строк освобождается только
после `VACUUM`, а вставки шли раньше, поэтому файлы росли. Вернуть место
операционной системе можно только `VACUUM FULL` или `pg_repack`, а это ещё
одна тяжёлая операция после решардинга.

# 6. Реализация Consistent Hashing

[`app/sharding/router.py`](../app/sharding/router.py):

```python
class ConsistentHashRouter:
    def __init__(self, nodes: list[str], vnodes: int = 100):
        self.nodes = list(nodes)
        # каждый шард ставится на кольцо vnodes раз: hash("shard-0#0"), hash("shard-0#1"), …
        points = sorted(
            (stable_hash(f"{node}#{i}"), node, i)
            for node in self.nodes for i in range(vnodes)
        )
        self._points = [p[0] for p in points]
        self._owners = [p[1] for p in points]

    def _position(self, h: int) -> int:
        """Первая точка кольца с координатой >= h; за концом кольцо замыкается."""
        i = bisect.bisect_left(self._points, h)
        return i if i < len(self._points) else 0

    def shard_for(self, key) -> str:
        return self._owners[self._position(stable_hash(key))]
```

Ровно по схеме из задания:

```
hash(shard_key)  →  точка на кольце 0 … 2^32-1  →  ближайший шард по часовой стрелке
```

Поиск — бинарный по отсортированному списку точек, `O(log(N · vnodes))`.
`vnodes=1` — базовая версия, одна точка на шард.

## Как это выглядит на кольце

`GET /api/shards/route/{user_id}` показывает путь ключа (кольцо из 4 шардов):

```
user 101: hash 951316472  → ближайшая точка 956867656  (shard-1#4)  → shard-1
user 102: hash 3968423523 → ближайшая точка 3997207076 (shard-3#83) → shard-3
user 103: hash 1769262682 → ближайшая точка 1778180315 (shard-3#2)  → shard-3
```

Для сравнения, `hash % 4` отправил бы их на shard-0, shard-3 и shard-2.

## Базовая версия и виртуальные узлы

Распределение 5 млн бронирований по 3 шардам:

| Стратегия | shard-0 | shard-1 | shard-2 | max/min | Худшее отклонение |
|---|---|---|---|---|---|
| `hash % 3` | 33.32 % | 33.16 % | 33.52 % | 1.011 | **0.56 %** |
| кольцо, `vnodes=1` | 22.37 % | **45.07 %** | 32.56 % | **2.015** | **35.22 %** |
| кольцо, `vnodes=10` | **42.82 %** | 26.99 % | 30.19 % | 1.587 | 28.46 % |
| кольцо, `vnodes=100` | 34.45 % | 34.71 % | 30.85 % | 1.125 | **7.46 %** |
| кольцо, `vnodes=200` | 29.67 % | 34.99 % | 35.34 % | 1.191 | 10.99 % |

Доля окружности, за которую отвечает каждый шард, почти точно повторяет доли данных:

```
vnodes=1    shard-0: 22.26 %  shard-1: 45.10 %  shard-2: 32.64 %
vnodes=100  shard-0: 34.57 %  shard-1: 34.66 %  shard-2: 30.77 %
```

**Базовая версия распределяет плохо.** Три точки на кольце встают случайно, и дуги
между ними получаются разной длины: shard-1 отвечает за 45 % окружности,
shard-0 — за 22 %. Один шард хранит вдвое больше соседа. Это ровно то, о чём
предупреждает лекция.

**Виртуальные узлы это лечат, но статистически.** С сотней точек на шард дуги
усредняются, и отклонение падает с 35 % до 7.5 %. Но `vnodes=200` оказался **хуже**
100 (11 % против 7.5 %). Разброс уменьшается пропорционально `1/√vnodes` лишь
в среднем, а конкретная раскладка точек — случайна. Больше виртуальных узлов —
выше шанс хорошей раскладки, но не гарантия.

Даже лучшее кольцо уступает `hash % N` в равномерности: 7.5 % против 0.56 %.
Это цена, которую consistent hashing платит за дешёвое изменение числа шардов.

## Объяснения

### 1. Почему результаты отличаются?

**Потому что стратегии по-разному зависят от N.**

В `hash % N` число шардов участвует в вычислении адреса **каждого** ключа.
Изменили N — изменилась функция целиком. Ключи перетасовываются между всеми
шардами, и сохраняется лишь случайное совпадение остатков.

В кольце позиция ключа — `hash(key)` — от числа шардов **не зависит вовсе**.
Добавление шарда меняет только одно: на кольце появляются новые точки. Ключ
меняет владельца, только если между ним и его прежним владельцем встала точка
нового шарда. Остальные ключи этого изменения не видят.

Матрицы переноса показывают это буквально. У `hash % N` заполнены все клетки,
то есть данные шли отовсюду и всюду. У кольца заполнен **один столбец** — всё
ехало только на новый shard-3.

### 2. Почему Consistent Hashing уменьшает объём перемещаемых данных?

Перемещается **ровно столько, сколько должен получить новый шард**, и ни строкой
больше. Новому шарду достаются дуги кольца перед его точками. Эти дуги он забирает
у тех шардов, которым они принадлежали раньше, а остальные дуги не меняются.

При идеальном балансе новый шард получает `1/N` кольца — 25 % при переходе
3 → 4. У нас перенеслось **31 %**, потому что shard-3 случайно занял 31.3 %
окружности:

```
ring_share_pct: shard-0: 21.9, shard-1: 24.57, shard-2: 22.23, shard-3: 31.3
```

Consistent hashing не обещает переносить ровно `1/N`. Он обещает переносить **ровно
долю нового шарда** — и только на него.

Следствие, которое легко упустить: **мало перенести ≠ хорошо**. Базовое кольцо
(`vnodes=1`) при 3 → 4 перенесло всего **5 %** — потому что новому шарду досталась
крохотная дуга. Данных почти не переехало, но и новый сервер почти ничего не взял
на себя. Добавляли его, чтобы разгрузить кластер, а он простаивает.

### 3. Что произойдёт, если добавить ещё один shard?

То же самое: переедет только доля нового шарда и только на него.
4 → 5 по кольцу — **19.96 %** (теория 1/5 = 20 %), и всё уходит на shard-4.
У `hash % N` — **79.82 %** (теория 80 %), с перетасовкой между всеми.

Разрыв **растёт с N**: у `hash % N` при переходе N → N+1 переезжает `N/(N+1)` данных,
то есть с ростом кластера почти всё. У кольца — `1/(N+1)`, то есть с ростом
кластера почти ничего. Чем больше кластер, тем дороже модуль и дешевле кольцо.

### 4. Что произойдёт, если удалить shard?

По кольцу **переезжают только данные удалённого шарда**, к соседям по часовой стрелке.
Остальные не трогаются. При удалении shard-1 из трёх переехало **1 735 461**
бронирование — это в точности всё, что лежало на shard-1 (строка `vnodes=100`
в таблице задания 6). Благодаря виртуальным узлам данные разошлись
по обоим оставшимся шардам: 1 013 648 на shard-0 и 721 813 на shard-2.
С одной точкой на шард они все упали бы на **одного** соседа и перегрузили его.

У `hash % N` удаление так же катастрофично, как добавление: **66 %** при 3 → 2,
**75 %** при 4 → 3. Переезжают и данные между выжившими шардами. Для незапланированного
отказа сервера это особенно плохо: система и так в аварии, а модуль требует
перетасовать почти всё.

### Интересный частный случай: удвоение

При **3 → 6** модуль перенёс **50 %** — столько же, сколько кольцо, и это минимум:
новым трём шардам и нужна половина данных. Когда новое N кратно старому,
`h % 6` однозначно определяет `h % 3`, и ключ либо остаётся на месте, либо уходит
на новый шард. Лишней перетасовки нет. Хуже всего модуль ведёт себя, когда
старое и новое N взаимно просты, как 3 и 4. Отсюда практика «удваивать кластер».

# 8. Итог

**Шард** — независимый экземпляр PostgreSQL, хранящий только свою часть данных.
Здесь их четыре, у каждого свой `system_identifier`, и никакой связи между ними нет.

**Shard key** — поле, по которому определяется шард записи. В сервисе это `user_id`:
50 000 значений, он есть во всех пользовательских запросах, и все бронирования
пользователя оказываются на одном сервере.

**Router** нужен, потому что сами шарды ничего друг о друге не знают. Кто-то должен
по ключу вычислить сервер — для записи и для чтения одинаково. У нас это чистый
модуль в коде сервиса, общий для API, загрузки и переноса данных.

**`hash(key) % N`** хэширует ключ и берёт остаток от деления на число шардов.
Распределение получается почти идеальным: отклонение 0.56 % на 5 млн бронирований.

**Проблема** в том, что N входит в формулу каждого ключа. При 3 → 4 шардах
переехало **75 % данных** (3.75 млн строк за 52.7 с), причём 2.5 млн — между старыми
шардами, которым это не было нужно.

**Consistent hashing** ставит и ключи, и шарды на одно кольцо, так что позиция ключа
от числа шардов не зависит. При 3 → 4 переехал **31 %** (1.55 млн строк за 18.7 с),
и только на новый шард. Цена — неравномерность: базовое кольцо отдало одному
шарду 45 % данных. Виртуальные узлы сократили перекос до 7.5 %, но полностью
его не убрали.

**Для своего сервиса я выбрал бы consistent hashing с виртуальными узлами.** Сервис
растёт, число шардов будет меняться, и платить 75 % переноса за каждое расширение
неприемлемо. Но я увеличил бы число виртуальных узлов и контролировал долю
каждого шарда на кольце: в нашем эксперименте shard-3 получил +24 % от идеала.
Промышленная альтернатива с тем же выигрышем и лучшим балансом — фиксированное
число логических корзин, например `hash % 1024`, с таблицей «корзина → сервер».
При расширении переезжают целые корзины, и баланс можно выравнивать вручную.
Так устроены Citus и Vitess.

# Вопросы для самопроверки

### 1. Что такое shard?

Независимый экземпляр базы данных, хранящий свою часть общих данных. В отличие
от реплики, шард — не копия, а **часть**: бронирование 5000006 существует только
на shard-1, остальные его не видят. В отличие от партиции, шард — отдельный
сервер со своим процессором, памятью и диском, а не таблица внутри той же базы.

### 2. Что такое shard key?

Поле записи, по которому router определяет её шард. У нас `user_id`. Хороший ключ:

- **высокая кардинальность** — значений намного больше, чем шардов
  (50 000 против 4);
- **есть в основных запросах** — иначе они превращаются в scatter-gather;
- **равномерная нагрузка** — нет значений, которые сами по себе создают
  горячий шард (как `event_id` популярного концерта);
- **неизменяемость** — если ключ поменяется, запись придётся переносить на
  другой сервер.

### 3. Почему нельзя просто случайно распределять записи между PostgreSQL?

Записать случайно легко — **найти потом невозможно**. Если шард выбран случайно,
никакое вычисление не скажет, где лежит запись, и **каждый** запрос придётся
отправлять на все шарды. Даже «мои бронирования» стали бы scatter-gather:
у нас это `X-Shards-Queried: 4` вместо `1`. К тому же бронирования одного
пользователя разбросало бы по всем шардам, и он не смог бы изменить их одной
локальной транзакцией.

Альтернатива случайности — хранить таблицу «запись → шард» (директивное
шардирование), но тогда сама эта таблица становится узким местом.
Хэш даёт ответ вычислением, без таблицы.

### 4. Как работает `hash(key) % N`?

Ключ превращается стабильной хэш-функцией в большое число, от него берётся остаток
от деления на число шардов:

```
hash(101) = 951316472;  951316472 % 3 = 2  → shard-2
```

Хэш нужен, чтобы перемешать ключи: даже последовательные `user_id` дают
непредсказуемые остатки, и шарды заполняются равномерно (0.56 % отклонения).
Хэш-функция обязана быть стабильной: встроенный `hash()` Python для этого
не подходит — см. задание 3.

### 5. Почему изменение количества shard'ов является проблемой?

При `hash % N` изменение N меняет адрес **большинства** записей: при переходе 3 → 4
переезжает 75 %, при 4 → 5 — 80 %, и с ростом кластера всё хуже.
Последствия, измеренные в работе:

- **объём** — 3.75 млн строк вместо необходимых 1.25 млн;
- **время** — 52.7 с на одной машине, на реальном кластере — часы;
- **раздувание** — старые шарды выросли с 236 до 355 MB при меньшем числе строк;
- **окно несогласованности** — пока идёт перенос, часть данных лежит не там,
  где их ищет router. Общей транзакции у независимых серверов нет.

### 6. Что такое Consistent Hash Ring?

Способ сопоставления ключей шардам, при котором и ключи, и шарды размещаются
на одном кольце значений хэш-функции (у нас 0 … 2³²−1). Шард ставится в точку
`hash("shard-1#4")`, ключ — в точку `hash(user_id)`. Ключ принадлежит первому шарду,
которого достигаешь, двигаясь от него по часовой стрелке. После последней точки
кольцо замыкается на первую.

```
user 101: hash 951316472 → ближайшая точка 956867656 (shard-1#4) → shard-1
```

### 7. Почему при добавлении shard'а не приходится переносить все данные?

Потому что позиция ключа на кольце — `hash(key)` — не зависит от числа шардов.
Новый шард лишь добавляет свои точки, и владельца меняют только ключи на дугах
перед этими точками. Все они переходят **на новый шард**. Между старыми шардами
не переезжает ничего — в эксперименте заполнен только столбец shard-3.
Переехал 31 % данных вместо 75 %.

### 8. Что такое virtual nodes и зачем они нужны?

Каждый физический шард ставится на кольцо не один, а много раз: `shard-0#0`,
`shard-0#1`, … `shard-0#99`. Зачем:

- **равномерность** — одна точка на шард даёт дуги случайной длины.
  В эксперименте: 45 % данных на одном шарде и 22 % на другом.
  Сто точек усредняют дуги, и перекос падает до 7.5 %;
- **распределение нагрузки при удалении** — данные удалённого шарда расходятся
  по всем соседям (1.01 млн и 0.72 млн), а не падают на одного;
- **учёт мощности серверов** — более мощному шарду можно дать больше виртуальных
  узлов, и он получит пропорционально больше данных.

### 9. Может ли Consistent Hashing гарантировать идеальное распределение нагрузки?

**Нет.** Измерено:

- **точки на кольце случайны** — даже со 100 виртуальными узлами шарды получили
  34.5 / 34.7 / 30.9 %, а после добавления четвёртого — 22 / 25 / 22 / **31 %**;
- **больше vnodes — не гарантия**: `vnodes=200` дал 11 % перекоса против 7.5 %
  у `vnodes=100`. Улучшение только статистическое, порядка `1/√vnodes`;
- **равенство строк ≠ равенство нагрузки** — хэш делит ключи, а не запросы.
  Пользователь-«кит» или шард с самыми активными пользователями даст перекос
  нагрузки при идеальном распределении строк;
- **`hash % N` распределяет ровнее** (0.56 %) — кольцо платит равномерностью
  за дешёвый решардинг.

### 10. Что произойдёт, если один shard станет значительно более загруженным остальных?

**Он станет узким местом всей системы.** Запросы пользователей с этого шарда
замедлятся, а если он откажет — эти пользователи не смогут ни читать,
ни бронировать, хотя остальные шарды простаивают. Добавить сервер «в общую кучу»
не поможет: нагрузка привязана к ключам, лежащим именно на этом шарде.

Что можно сделать:

- **расщепить горячий шард** — в кольце добавить точки нового шарда в его дугу,
  тогда переедут только его данные;
- **перераспределить виртуальные узлы** — снять часть точек с перегруженного шарда;
- **вынести горячие ключи отдельно** — для «кита» таблица-исключение
  «ключ → выделенный шард» поверх хэша;
- **добавить реплики горячему шарду** — чтение разгрузится (ЛР4), запись — нет;
- **сменить стратегию на корзины** — фиксированные логические корзины
  переносятся между серверами поштучно.

Дисбаланс нужно замечать заранее: `GET /api/shards` показывает долю каждого
шарда и отклонение от идеала.

# Ограничения

- **Шардированный API работает параллельно с основным.** `/api/shards/...` читает
  и пишет шарды, а прежние `/api/bookings` и `/api/users/{id}/bookings` по-прежнему
  работают с primary, где остались все 5 млн бронирований. Перевести сервис целиком
  значило бы сломать партиционирование и реплики из ЛР3–4 и переписать всю
  аналитику на scatter-gather. Для лабораторной выбран параллельный путь;
  в реальном переходе исходную таблицу выводят из обращения после миграции.
- **Смена конфигурации router'а — перезапуском бэкенда** и только после переноса
  данных. Нет двойной записи на время миграции, нет ступенчатого переключения
  по пользователям.
- **Перенос не атомарен.** Строки кратко существуют и на исходном, и на целевом
  шарде; распределённой транзакции нет. Скрипт идемпотентен: повторный запуск
  после сбоя не создаст дубликатов.
- **Все шарды на одном компьютере**, поэтому время переноса занижено: нет сети
  между серверами.
- **Реплик у шардов нет** — отказ шарда недоступен его пользователям. В реальной
  системе у каждого шарда своя пара primary + replica.
