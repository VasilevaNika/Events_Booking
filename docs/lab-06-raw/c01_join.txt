  bookings  5 млн строк  — на шардах, по user_id    (на primary: 981 MB)

  2. Если бы мероприятия тоже шардировались — по event_id
──────────────────────────────────────────────────────────────────────────────
  бронирований, у которых мероприятие на том же шарде: 1 278 966 из 5 000 005 (25.58 %)
  остальные 74.42 % — JOIN между разными серверами

  пользователь 101, 20 последних бронирований (шард бронирований: shard-1):
    мероприятия лежат на 4 шардах; 15 из 20 — не на шарде пользователя

──────────────────────────────────────────────────────────────────────────────
  3. Решение: копия справочников на каждом шарде (reference tables)
──────────────────────────────────────────────────────────────────────────────
  shard-0: events 2 000, venues 200, вместе 416 kB
  shard-1: events 2 000, venues 200, вместе 416 kB
  shard-2: events 2 000, venues 200, вместе 416 kB
  shard-3: events 2 000, venues 200, вместе 416 kB

  план JOIN на shard-1:
    Limit  (cost=0.85..124.07 rows=20 width=144) (actual time=0.019..0.129 rows=20 loops=1)
      ->  Nested Loop  (cost=0.85..616.93 rows=100 width=144) (actual time=0.018..0.127 rows=20 loops=1)
            ->  Nested Loop  (cost=0.71..599.68 rows=100 width=97) (actual time=0.015..0.102 rows=20 loops=1)
                  ->  Index Scan using ix_bookings_user_id_created_at on bookings b  (cost=0.43..406.18 rows=100 width=20) (actual time=0.009..0.028 rows=20 loops=1)

            ->  Index Scan using venues_pkey on venues v  (cost=0.14..0.17 rows=1 width=55) (actual time=0.001..0.001 rows=1 loops=20)

  5. А если сделать shard key = event_id?
──────────────────────────────────────────────────────────────────────────────
  bookings ⋈ events станет локальным всегда — бронирование и его мероприятие
  окажутся на одном шарде по построению. Цена — «мои бронирования»:

  то есть запрос пользователя превратится в scatter-gather.
