# 1. Архитектура после шардирования

```
                         Backend (FastAPI)
                                │
            ┌───────────────────┴────────────────────┐
            │                                        │
          Router  (hash(user_id) → точка на кольце)   Primary
            │                                        users, events, venues
  ┌─────────┼─────────┬─────────┐                    (справочники)
  ▼         ▼         ▼         ▼
shard-0   shard-1   shard-2   shard-3
bookings  bookings  bookings  bookings   + копия events/venues (задание 4)
```

## Все реальные запросы сервиса после шардирования

| Endpoint | Что читает | Где выполняется |
|---|---|---|
| `GET /api/users/{id}/bookings` | бронирования пользователя | **1 шард** |
| `GET /api/users/{id}/stats` | COUNT/SUM/AVG по пользователю | **1 шард** |
| `POST /api/bookings` | `user_id` в теле | **1 шард** |
| `GET /api/bookings/{id}` | по id бронирования | **все шарды** — id не shard key |
| `PUT`, `DELETE /api/bookings/{id}` | по id | **все шарды**, чтобы найти, затем 1 |
| `GET /api/bookings?status=&from_date=` | список всех бронирований + `COUNT(*)` | **все шарды** + слияние |
| `GET /api/events/{id}/bookings` | бронирования мероприятия | **все шарды** — `event_id` не shard key |

Три запроса — одношардовые, шесть — распределённые. Пользовательские сценарии
(«мои бронирования», «моя статистика», «забронировать») остались на одном сервере.
Распределёнными стали административные и аналитические сценарии, а также поиск
по id.

# 2. Single-Shard Query

**Запрос:** «мои бронирования» — `BookingRepository.get_by_user_id`:

```sql
SELECT b.id, b.user_id, b.event_id, b.status, b.seats_count, b.total_price, b.created_at,
       e.title, e.start_time, v.name
FROM bookings b
JOIN events e ON b.event_id = e.id
JOIN venues v ON e.venue_id = v.id
WHERE b.user_id = ?
ORDER BY b.created_at DESC
LIMIT 20
```

## Почему запросу не нужны другие шарды

В условии есть shard key — `user_id = 101`. Router вычисляет шард **до** выполнения
запроса, по одному значению:

```
hash(101) = 951316472 → ближайшая точка кольца 956867656 (shard-1#4) → shard-1
```

Router и загрузка данных используют одну и ту же функцию. Поэтому **все**
бронирования пользователя 101 лежат только там, куда указывает router:

```
shard-0:    0 бронирований
shard-1:  104 бронирований  ← router
shard-2:    0 бронирований
shard-3:    0 бронирований
```

Спрашивать остальные шарды бессмысленно: строк пользователя 101 на них нет
по построению. Это гарантия, а не вероятность.

## Замер

План на шарде и на primary для того же запроса:

| | План | Прочитано страниц | Planning | Execution |
|---|---|---|---|---|
| **shard-1** (1.2 млн строк) | `Index Scan` по одной таблице | 23 | 0.186 мс | **0.112 мс** |
| **primary** (5 млн строк, 17 партиций) | `Merge Append` по 17 партициям | 73 | 1.530 мс | **0.551 мс** |

Время ответа API, 50 запросов:

| Вариант | p50 | Шардов опрошено |
|---|---|---|
| Шарды, JOIN в приложении | 11.97 мс | 1 |
| Шарды, JOIN на шарде | 10.39 мс | 1 |
| Primary, основное API | 11.74 мс | — |

На уровне БД запрос на шарде в **5 раз быстрее**: одна таблица и один индекс вместо
обхода 17 партиций (ЛР3). Но в ответе API разницы нет — 10–12 мс у всех вариантов.
Полмиллисекунды в базе тонут в HTTP, сериализации JSON и работе FastAPI.

## Агрегация с shard key — тоже один шард

`GET /api/shards/users/101/stats` — `COUNT`, `SUM`, `AVG` бронирований пользователя:

```
шарды  [shard-1, опрошено 1]: бронирований 84, потрачено 183473.98, средний чек 2184.21
primary:                     бронирований 84, потрачено 183473.98, средний чек 2184.21
```

Агрегация сама по себе не делает запрос распределённым. Распределённым его делает
**отсутствие shard key**.

# 3. Агрегирующий запрос

## `COUNT(*)` по всем шардам

```
shard-0 →   1 101 949
shard-1 →   1 232 345
shard-2 →   1 114 852
shard-3 →   1 550 859
           -----------
сумма   →   5 000 005
primary →   5 000 005   совпадает
```

## Выручка по мероприятиям

Реальный запрос — `BookingRepository.get_revenue_by_event`: для каждого мероприятия
`COUNT` бронирований, `SUM` мест, `SUM` и `AVG` выручки. На шардах он выполняется
в два этапа.

**Этап 1 — на каждом шарде, параллельно:** частичные агрегаты.

```sql
SELECT event_id, count(*), sum(seats_count), sum(total_price)
FROM bookings WHERE status <> 'cancelled'
GROUP BY event_id
```

**Этап 2 — в приложении:** сложить по `event_id` и присоединить названия
мероприятий с primary.

```
шарды вернули 8 000 частичных групп → после слияния 2000 мероприятий
расхождений с эталоном: 0 из 2000; наибольшая разница выручки 0.0000
```

| Мероприятие | Шарды | Primary |
|---|---|---|
| 815 | 5 162 974.50 (2045 броней) | 5 162 974.50 |
| 515 | 5 089 786.36 (2002 брони) | 5 089 786.36 |
| 1639 | 5 086 988.56 (2036 броней) | 5 086 988.56 |

## Ловушка: AVG нельзя усреднить

Каждое мероприятие есть на всех четырёх шардах. Мероприятие 911:

| Шард | Бронирований | Средний чек на шарде |
|---|---|---|
| 1 | 408 | 2306.72 |
| 2 | 439 | 2499.63 |
| 3 | 381 | 2456.29 |
| 4 | 590 | 2680.89 |
| **среднее средних** | | **2485.88 — неверно** |
| **SUM / COUNT по всем шардам** | | **2506.08 — верно, как на primary** |

Среднее средних придаёт шарду с 381 бронированием тот же вес, что шарду с 590.
**Ошибка больше 1 ₽ — у 1640 мероприятий из 2000.**

Правило: каждый шард возвращает не готовое среднее, а **сумму и количество**.
Итоговое среднее считается одно — в конце.

То же касается других агрегатов:

- `SUM`, `COUNT`, `MIN`, `MAX` сливаются прямо: сумма сумм, минимум минимумов;
- `AVG` — только через `SUM` и `COUNT`;
- медиану и `COUNT(DISTINCT)` так разложить нельзя вообще: `DISTINCT` по пользователям,
  лежащим на разных шардах, требует передать сами значения, а не счётчики.

## Ответы

### 1. Можно ли выполнить такой запрос только на одном shard?

**Нет.** У каждого мероприятия бронирования от пользователей со всех шардов.
Мероприятие 911 — 408 + 439 + 381 + 590 бронирований на четырёх разных серверах.
Результат любого одного шарда — это часть, а не ответ. При шардировании по `user_id`
выручка по мероприятию — распределённый запрос всегда.

### 2. Где должны объединяться результаты?

На **координаторе** — в нашем случае это бэкенд. Шарды не знают друг о друге
и не могут обменяться данными. Бэкенд рассылает запрос, собирает частичные
агрегаты и сливает их. Слияние 8000 частичных групп заняло **5.3 мс** против
сотен миллисекунд на самих шардах. Важно, что шарды возвращают **агрегаты**
(8000 строк), а не бронирования (5 млн). Тяжёлую работу выполняют шарды,
координатор только складывает.

### 3. Что происходит со временем выполнения при увеличении количества shard'ов?

Два противоположных эффекта, оба измерены.

**Работа на шарде уменьшается.** Каждый шард агрегирует свою четверть данных:

| Способ | Время |
|---|---|
| **Primary, запрос как в `BookingRepository`** | **18 403.6 мс** |
| Primary, тот же расчёт в форме «сначала агрегация, потом JOIN» | 756.1 мс |
| Шарды, по очереди | 782.6 мс |
| **Шарды, параллельно** | **587.7 мс** (shard-0 359, shard-1 382, shard-2 333, shard-3 433 мс; слияние 5.3 мс) |

**Но растёт цена обращения к шардам и ожидание самого медленного.**

Цена самого обращения (`SELECT 1`, 200 повторов):

| Шардов | По очереди | Параллельно |
|---|---|---|
| 1 | 1.55 мс | 1.43 мс |
| 2 | 2.90 мс | 1.90 мс |
| 4 | 5.54 мс | 3.05 мс |
| 8 | 11.77 мс | 11.09 мс |
| 16 | 24.18 мс | 20.19 мс |

Когда шарды отвечают с разной скоростью (случайная задержка 0–20 мс), параллельный
ответ ждёт **самого медленного**:

| Шардов | Параллельно, p50 | Медиана максимума `20·0.5^(1/k)` |
|---|---|---|
| 1 | 14.62 мс | 10.00 мс |
| 2 | 16.47 мс | 14.14 мс |
| 4 | 21.44 мс | 16.82 мс |
| 8 | 24.37 мс | 18.34 мс |
| 16 | 29.63 мс | 19.15 мс |

Вывод по времени:

- **По очереди** время растёт линейно: сумма времени всех шардов.
- **Параллельно** время = самый медленный шард + цена координации. С ростом числа шардов
  растёт вероятность, что хоть один ответит медленно. Это «хвостовая задержка»:
  при 16 шардах медиана ответа — 29.6 мс, хотя медиана одного шарда 10 мс.
- **Для тяжёлого агрегата** выигрыш есть, пока работа шарда больше цены координации.
  Для лёгкого запроса вроде `COUNT` по 4 шардам цена обращений сравнима с самой работой.
- **Параллелизм здесь ограничен железом.** Все шарды на одном компьютере, поэтому
  параллельно каждый работал в 2.5 раза медленнее, чем по очереди (359 против 145 мс
  у shard-0): они делят процессор и диск. На отдельных серверах выигрыш был бы близок к 4×.
  Для совсем мелких запросов параллельность упирается в сам Python-координатор:
  при 8 и 16 обращениях параллельный вариант почти не быстрее последовательного.

### Главная находка: 18.4 секунды на primary

Разница «18 403 мс на primary против 588 мс на шардах» выглядит как успех шардирования.
Но **основную её часть дало не шардирование**:

- Запрос `get_revenue_by_event` в сервисе получил на primary плохой план:
  `Nested Loop` по 2000 мероприятиям, и для каждого — поиск по индексу **в каждой
  из 17 партиций**. Это 34 000 отдельных поисков, 3.7 млн строк на выходе,
  затем их сортировка и только потом группировка.
- Шардирование **вынудило** переписать запрос в форму «сначала агрегируй
  по `event_id`, потом присоедини 2000 строк»: иначе частичные агрегаты
  на шардах не посчитать.
- **Тот же переписанный запрос на одном primary — 756 мс.** Шарды к этому добавили
  только 1.3× (756 → 588 мс).

Иначе говоря: **перестройка запроса дала 24×, шардирование — 1.3×.**
В основном API это настоящий дефект производительности, и он исправляется
без всякого шардирования. В отчёт он не вносился как исправление — только
зафиксирован.

# 4. JOIN между shard'ами

**JOIN сервиса:** `bookings ⋈ events ⋈ venues` — в `get_by_user_id`, `get_all`
и `get_revenue_by_event`. К бронированию присоединяются название мероприятия
и площадка.

## Где находятся связанные данные

| Таблица | Строк | Где | Размер |
|---|---|---|---|
| `bookings` | 5 000 005 | шарды, по `user_id` | 981 MB на primary |
| `events` | 2 000 | primary | 1 768 kB |
| `venues` | 200 | primary | 152 kB |

Бронирование на шарде, его мероприятие — на другом сервере.
В SQL это не соединить.

## Если бы мероприятия тоже шардировались

Что если `events` разложить по шардам тем же router'ом, но по `event_id`?
Расчёт на всех 5 млн бронирований:

```
бронирований, у которых мероприятие на том же шарде: 1 278 966 из 5 000 005 (25.58 %)
остальные 74.42 % — JOIN между разными серверами
```

**74 % соединений оказались бы межсерверными.** 25.58 % — не случайное число:
это вероятность того, что два независимых ключа попадут на один шард,
`Σ доля_i²` = 0.220² + 0.247² + 0.223² + 0.310² ≈ 0.256.

Для одного пользователя: 20 последних бронирований пользователя 101 лежат на shard-1,
а их мероприятия — **на всех 4 шардах, 15 из 20 не на shard-1**.

## Решение: копия справочников на каждом шарде

Мероприятия и площадки — маленькие справочники, они меняются редко. Их полная
копия лежит на каждом шарде (reference tables, или broadcast tables).
[`sync_reference.py`](../scripts/lab06/sync_reference.py):

```
shard-0: events 2 000, venues 200, вместе 416 kB
shard-1: events 2 000, venues 200, вместе 416 kB
shard-2: events 2 000, venues 200, вместе 416 kB
shard-3: events 2 000, venues 200, вместе 416 kB
копии справочников обновлены на всех шардах за 459 мс
```

Теперь JOIN выполняется **на шарде обычным SQL**:

```
Limit  (actual time=0.026..0.089 rows=20)
  ->  Nested Loop
        ->  Nested Loop
              ->  Index Scan using ix_bookings_user_id_created_at on bookings b
                    Index Cond: (user_id = 101)
              ->  Index Scan using events_pkey on events e
        ->  Index Scan using venues_pkey on venues v
Execution Time: 0.123 ms
```

`GET /api/shards/users/{id}/bookings?join=local` возвращает **те же строки**,
что вариант с JOIN в приложении:

| Вариант | Серверов | p50 API |
|---|---|---|
| JOIN в приложении | 2 — шард + primary | 11.45 мс |
| **JOIN на шарде** | **1** | **10.37 мс** |
| Primary, основное API | 1 | 11.59 мс |

Цена копии — **её надо обновлять**. Переименовали мероприятие на primary —
копии на шардах устарели, пока их не перезальют. `sync_reference.py` — простейший
вариант с полной перезаливкой. В реальной системе копию держат логической
репликацией или событием «мероприятие изменено».

## Ответы

### 1. Что произойдёт, если связанные записи находятся на разных shard'ах?

Базе их не соединить: шард `A` ничего не знает о строках шарда `B`. Соединять
придётся приложению — прочитать строки с одного сервера, затем связанные строки
с другого, склеить в памяти. Это уже так работает в нашем «JOIN в приложении»:
бронирования с шарда, мероприятия с primary. При 74 % межсерверных соединений
почти каждый запрос требовал бы нескольких сетевых обращений.

### 2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?

**Нет.** Один SQL-запрос выполняется одним сервером и видит только его таблицы.
Обходные пути — `postgres_fdw`, распределённые СУБД вроде Citus — делают то же
перемещение данных, только внутри себя. Бесплатного распределённого JOIN не бывает.

### 3. Какие данные пришлось бы передавать между shard'ами?

Для соединения одну сторону приходится везти туда, где лежит другая.
Выбор — **что дешевле перевезти**:

- **справочники** — 2 000 мероприятий и 200 площадок, **416 kB** — можно
  один раз положить на каждый шард;
- **бронирования** — 5 млн строк, **981 MB** — возить нельзя.

Для «моих бронирований» без копии: 20 бронирований с одного шарда и 20 мероприятий
с четырёх (при шардировании мероприятий) — 5 обращений вместо одного.
Для выручки: 5 млн бронирований против 2000 мероприятий — везут меньшую сторону
или предварительно агрегированную: 8000 частичных групп вместо 5 млн строк,
как в задании 3.

### 4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри одного shard?

Да, но за счёт других запросов:

- **`event_id` в качестве ключа** и для бронирований, и для мероприятий — JOIN
  всегда локальный. Цена: 20 последних бронирований пользователя 101 разошлись бы
  по 4 шардам, и «мои бронирования» стали бы scatter-gather.
- **Колокация по одному ключу.** Если шардировать `users` тоже по `user_id`,
  соединение `bookings ⋈ users` из `get_all` станет локальным всегда: пользователь
  и его брони попадают на один шард по построению. Так работают co-located таблицы
  в Citus.
- **Reference tables для маленьких справочников** — лучшее решение для
  `events` и `venues`, реализовано выше.

Итог: выбирать ключ под **самые частые** запросы, а маленькие справочники
копировать на каждый шард.

# 5. ORDER BY + LIMIT

**Запрос:** последние бронирования системы — `BookingRepository.get_all`
с сортировкой по умолчанию:

```sql
SELECT ... FROM bookings ORDER BY created_at DESC LIMIT 20 OFFSET ?
```

Эталон — 20 последних бронирований на primary.

## Топ-20 только с одного шарда

| Шард | Из его топ-20 попали в настоящий топ-20 | Пропущено |
|---|---|---|
| shard-0 | 7 | 13 |
| shard-1 | 3 | 17 |
| shard-2 | 3 | 17 |
| shard-3 | 7 | 13 |

## «Поровну» — по 5 с каждого

Совпало **16 из 20**. Свежие бронирования распределены неравномерно:
в настоящем топе 7 строк с shard-0 и только 3 с shard-1.

## Правильно: топ-20 с каждого шарда → слияние

```
опрошено шардов: 4, получено строк с шардов 80, отдано 20
совпадает с эталоном: да, все 20 в том же порядке
откуда пришли строки итогового топа: shard-0: 7, shard-1: 3, shard-2: 3, shard-3: 7
```

Каждый шард возвращает свой топ-20, отсортированный по `(created_at, id)`.
Бэкенд сливает четыре отсортированных списка (`heapq.merge`) и берёт первые 20.

### Почему недостаточно получить первые 100 записей только с одного shard?

Потому что шард не знает, что лежит на других. Первые 20 записей shard-1 — это его
самые свежие бронирования, но **17 из них проигрывают** более свежим с других шардов.
Router раскладывает по `user_id`, а не по времени, поэтому свежие бронирования
разбросаны по всем шардам в непредсказуемой пропорции (7 : 3 : 3 : 7).

Чтобы гарантированно получить глобальный топ-N, нужен топ-N **с каждого** шарда:
в худшем случае все N лежат на одном. Меньше брать нельзя — «поровну» дало 16 из 20.

## Глубокие страницы: OFFSET

Для страницы с `OFFSET k` каждый шард обязан вернуть `k + 20` строк: заранее
неизвестно, сколько из них войдёт в итоговую страницу.

| offset | Строк с шардов | Шарды, мс | Primary, мс | Совпало с primary |
|---|---|---|---|---|
| 0 | 80 | 4.8 | 1.0 | да |
| 1 000 | 4 080 | 15.6 | 3.6 | да |
| 10 000 | 40 080 | 162.9 | 8.2 | да |
| **100 000** | **400 080** | **2 455.1** | 90.7 | да |

**Чтобы отдать 20 строк страницы 5001, с шардов пришлось получить 400 080 строк.**
Число прочитанных строк растёт как `N_шардов × (offset + limit)`.
На primary глубокая страница тоже дорожает, но в 27 раз меньше.

## Решение: keyset-пагинация

Вместо номера страницы клиент передаёт курсор — `created_at` и `id` последней
показанной строки. Каждый шард отдаёт 20 строк **после** курсора:
`WHERE (created_at, id) < (:c, :id)`, по индексу `(created_at DESC, id DESC)`.

| Страница с | Строк с шардов | Шарды, мс | Совпало со страницей OFFSET |
|---|---|---|---|
| 1 000 | 80 | 5.1 | да |
| 10 000 | 80 | 5.2 | да |
| 100 000 | 80 | 4.7 | да |

**Постоянные 80 строк и 5 мс на любой глубине** — против 400 080 строк
и 2.5 с при `OFFSET`. Цена: нельзя перейти сразу на страницу 5000,
только «следующая» и «предыдущая».

# 6. Отказ одного shard

Сценарий [`e01_shard_failure.sh`](../scripts/lab06/e01_shard_failure.sh):
`docker stop booking_shard_2`, вызов всех эндпоинтов, затем `docker start`.

## Результат: shard-2 недоступен

| | Endpoint | HTTP | мс | Ответ |
|---|---|---|---|---|
| шарды | бронирования пользователя с shard-0 | **200** | 29.9 | работает |
| шарды | бронирования пользователя с shard-2 | **503** | 496.1 | `shard-2 не отвечает` |
| шарды | статистика пользователя с shard-2 | **503** | 16.3 | |
| шарды | POST бронирование пользователю с shard-2 | **503** | 30.7 | |
| шарды | бронь по id, лежит на shard-0 | **200** | 14.2 | нашлась на доступном шарде |
| шарды | бронь по id, лежит на shard-2 | **503** | 15.6 | |
| шарды | **несуществующая** бронь по id | **503** | 15.5 | не 404! |
| шарды | `COUNT(*)` по всем шардам | **503** | 203.1 | |
| шарды | то же, `allow_partial=true` | **200** | 99.7 | `partial=true, total=3885153, без: shard-2` |
| шарды | выручка по мероприятиям | **503** | 423.5 | |
| шарды | то же, `allow_partial=true` | **200** | 500.0 | `partial=true` |
| шарды | последние бронирования | **503** | 23.6 | |
| шарды | обзор шардов | **200** | 716.6 | shard-2 — `down` |
| primary | каталог мероприятий, пользователь, /health | **200** | 10–60 | не затронуты |

После `docker start` все эндпоинты снова ответили **200**, несуществующая бронь —
снова **404**, `COUNT` — снова полные 5 000 005. Пул соединений бэкенда
восстановился сам: `pool_pre_ping` отбрасывает мёртвые соединения.

## Ответы

### 1. Какие данные становятся недоступны?

**Все бронирования 11 150 пользователей, чьи ключи ведут на shard-2** —
1 114 852 бронирования, 22.3 % данных. Не «случайные 22 % бронирований», а **все**
бронирования **конкретных** людей: для них сервис бронирований отключён полностью,
для остальных 77.7 % пользователей не изменилось ничего.

Справочники на primary — пользователи, мероприятия, площадки — доступны.

### 2. Какие endpoint'ы перестанут работать?

- **Одношардовые — только для пользователей shard-2**: «мои бронирования»,
  «моя статистика», оформление брони. Для остальных пользователей работают.
- **Распределённые — для всех**: `COUNT`, выручка, последние бронирования.
  Без четверти данных их ответ был бы **неверным**, а не неполным.
- **Поиск по id** — частично: бронь, найденная на живом шарде, отдаётся.
  А вот **отсутствие брони доказать нельзя**: вдруг она на shard-2?
  Поэтому несуществующая бронь даёт 503, а не 404.

### 3. Продолжит ли работать остальная часть сервиса?

**Да.** Каталог мероприятий, пользователи, площадки, `/health`, бронирования 77.7 %
пользователей — всё отвечает 200. Отказ шарда — это частичная деградация,
а не падение сервиса. В этом преимущество шардирования перед одним сервером:
при отказе единственного primary недоступно было бы всё.

### 4. Что должен делать backend при обращении к недоступному shard?

Реализовано в сервисе:

- **503 вместо 500.** Отказ шарда — временная недоступность, а не ошибка кода.
  Ответ содержит, какой шард недоступен, и `Retry-After: 30`
  ([`app/main.py`](../app/main.py)).
- **Не превращать «не знаю» в «нет».** Если шард недоступен и запись не найдена
  на остальных — 503, а не 404. Ответ «брони нет» при недоступном шарде мог бы
  заставить пользователя оформить её повторно.
- **Неполный ответ — только по явному запросу.** Сумма без шарда по умолчанию — 503.
  Если потребителю допустимо приблизительное значение, он просит `allow_partial=true`
  и получает ответ с флагом `partial: true` и списком недоступных шардов.
- **Быстро отказывать.** Первое обращение к остановленному шарду заняло 496 мс,
  следующие — 15–30 мс. У подключения стоит `connect_timeout=3`.

Не реализовано, но нужно в продакшене: **circuit breaker** (перестать стучаться
в мёртвый шард на N секунд) и **таймаут на запрос**. Опаснее всего не упавший,
а **зависший** шард: соединение открыто, но ответа нет. Без таймаутов
на стороне приложения такой запрос висит, пока не кончатся потоки бэкенда.

### 5. Как можно повысить отказоустойчивость?

- **Реплика у каждого шарда** (ЛР4): при отказе — переключение на реплику.
  Чтение продолжается сразу, запись — после повышения реплики.
- **Автоматический failover** — Patroni или аналог для каждой пары primary + replica.
- **Кэш «горячих» данных** — «мои бронирования» можно отдавать из кэша,
  пока шард недоступен.
- **Очередь записей** — оформление брони можно принять в очередь и провести
  после восстановления шарда, а не отказывать.
- **Больше шардов** — отказ одного из 16 задевает 6 % пользователей, а не 22 %.
  Но шардов больше — и отказы случаются чаще.

# 7. Hot Shard

Данные по шардам распределены: 22.04 / 24.65 / 22.30 / 31.02 %.
[`f01_hot_shard.py`](../scripts/lab06/f01_hot_shard.py) проверяет, как распределится
**нагрузка** при разном составе запросов. Нагрузка считается двумя независимыми
способами: счётчиком запросов в бэкенде и счётчиками самого PostgreSQL
(`pg_stat_database`: транзакции и прочитанные строки).

## A. Равномерный трафик

2000 запросов «мои бронирования» от случайных пользователей:

| Шард | Доля данных | Запросов | Доля запросов | Прочитано строк |
|---|---|---|---|---|
| shard-0 | 22.04 % | 428 | 21.40 % | 21.73 % |
| shard-1 | 24.65 % | 481 | 24.05 % | 24.01 % |
| shard-2 | 22.30 % | 453 | 22.65 % | 22.14 % |
| shard-3 | 31.02 % | 638 | 31.90 % | 32.12 % |

Нагрузка повторяет распределение данных.

## B. Популярный пользователь

70 % запросов — от одного пользователя (6, лежит на shard-2), остальные 30 % — случайные:

| Шард | Доля данных | Запросов | **Доля запросов** | Прочитано строк |
|---|---|---|---|---|
| shard-0 | 22.04 % | 134 | 6.70 % | 7.89 % |
| shard-1 | 24.65 % | 141 | 7.05 % | 8.56 % |
| **shard-2** | **22.30 %** | **1 545** | **77.25 %** | **73.53 %** |
| shard-3 | 31.02 % | 180 | 9.00 % | 10.02 % |

**shard-2 хранит 22 % данных и получает 77 % запросов** — ровно ситуация из задания
(10 % / 15 % / 75 %). Строк на нём столько же, сколько на соседях.

## C. Тип запроса

1000 запросов «мои бронирования» и 50 отчётов о выручке:

| Шард | Доля данных | Запросов | Доля запросов | **Прочитано строк** | Доля строк |
|---|---|---|---|---|---|
| shard-0 | 22.04 % | 265 | 22.08 % | 55 146 104 | 22.09 % |
| shard-1 | 24.65 % | 291 | 24.25 % | 61 667 344 | 24.70 % |
| shard-2 | 22.30 % | 251 | 20.92 % | 55 792 694 | 22.35 % |
| shard-3 | 31.02 % | 393 | 32.75 % | 77 058 474 | 30.86 % |

1 050 HTTP-запросов превратились в **1 200 запросов к шардам**: каждый отчёт
о выручке — это 4 запроса. 50 отчётов — **5 % HTTP-запросов**, но они прочитали
**~250 млн строк**. 1000 пользовательских запросов прочитали около 40 тысяч.
Нагрузку определил не трафик, а **тип** запроса, и самый большой шард (31 % данных)
получил самую большую долю тяжёлой работы.

## Возможные причины горячего шарда

| Причина | Как проявляется | Пример в сервисе |
|---|---|---|
| **неудачный shard key** | мало значений или естественные пики | `event_id`: старт продаж на концерт — все записи в один шард; `created_at`: вся запись в «последний» шард |
| **неравномерное распределение данных** | одному шарду досталась большая дуга кольца | shard-3 после добавления в ЛР5 — 31 % данных вместо 25 % |
| **популярный пользователь / tenant** | один ключ генерирует непропорциональный трафик | сценарий B: один пользователь → 77 % запросов |
| **определённый тип запросов** | тяжёлые запросы бьют по всем шардам пропорционально данным | сценарий C: 5 % запросов → почти вся прочитанная работа |

## Почему равное количество строк ещё не означает равномерную нагрузку?

Router делит поровну **ключи**, а не **обращения к ним**. Нагрузку создают запросы,
а к разным ключам обращаются с очень разной частотой.

В сценарии B строк на всех шардах примерно поровну, но один активный пользователь
увёл 77 % запросов на свой шард. Хэш не может разделить одного пользователя
на несколько шардов: все его данные — на одном по построению. И чем лучше
shard key держит данные пользователя вместе, тем сильнее его личная активность
нагружает один сервер.

К тому же стоимость запросов различается на порядки. Одна «выручка»
читает 1.1–1.5 млн строк на каждом шарде, а «мои бронирования» — 20.
Равное число строк означает равный **объём**, а нагрузка — это **частота × стоимость**
обращений.

# 8. Итоговый анализ shard key

## Подходит ли `user_id` для сервиса?

**Да, подходит.** Он делает быстрыми и отказоустойчивыми именно пользовательские
сценарии — самые частые и самые чувствительные к задержке. Но распределёнными
становятся вся аналитика и поиск по id бронирования. Это нужно компенсировать
не выбором другого ключа, а архитектурой вокруг него.

## Плюсы — эффективные запросы

| Запрос | Почему эффективен |
|---|---|
| «Мои бронирования» | 1 шард, 23 страницы, 0.112 мс в БД — в 5 раз быстрее primary |
| «Моя статистика» (`COUNT`, `SUM`, `AVG`) | 1 шард, результат совпадает с primary |
| Оформление бронирования | 1 шард, одна локальная транзакция |
| JOIN бронирований с пользователем | при шардировании `users` по тому же ключу — всегда локальный |
| Отказ шарда | задевает 22 % пользователей, остальные не замечают |

## Минусы — распределённые запросы

| Запрос | Цена |
|---|---|
| Выручка по мероприятиям | все шарды + частичные агрегаты + ловушка с AVG |
| Бронирования мероприятия (`/events/{id}/bookings`) | все шарды |
| Список всех бронирований + `COUNT(*)` | все шарды; глубокие страницы — 400 080 строк за 20 |
| Бронь по id | все шарды; при отказе одного даже «не найдено» становится 503 |
| JOIN с мероприятиями | межсерверный, пока нет копии справочников |

## Проблемные операции

| Операция | Сложность | Что показала работа |
|---|---|---|
| **JOIN** | высокая, но решаемая | 74 % соединений межсерверные при шардировании мероприятий; копия справочников на 416 kB делает JOIN локальным |
| **Aggregation** | средняя | частичные агрегаты сливаются точно (0 расхождений из 2000), но AVG, медиана, `COUNT(DISTINCT)` требуют аккуратности; ошибка «среднего средних» — у 82 % мероприятий |
| **ORDER BY** | средняя, с OFFSET — высокая | топ-N — слияние N×шардов строк; глубокая страница — 400 080 строк за 20; keyset решает |
| **Migration** (решардинг) | **очень высокая** | ЛР5: 3 → 4 шарда — 3.75 млн строк при `hash % N`, 1.55 млн по кольцу; разбухание таблиц; нет общей транзакции |
| **Backup** | высокая | у каждого шарда свой `pg_dump`/WAL; нет одного момента времени на все шарды — бэкапы снимаются в разные моменты и не согласованы между собой и с primary |
| **Восстановление** | **очень высокая** | восстановленный на вчера шард рассогласован с остальными: его пользователи «потеряли» сегодняшние брони, а последовательность id на primary ушла вперёд |
| **Балансировка** | высокая | shard-3 получил 31 % данных; популярный пользователь сделал shard-2 горячим — хэшем это не исправить, нужен перенос пользователя или дробление |

**Самые сложные — миграция и восстановление.** Остальные операции касаются одного
запроса и решаются кодом. Эти две касаются **всех данных** и **всех серверов сразу**,
при этом распределённой транзакции и общей точки во времени у независимых
PostgreSQL нет.

## Вывод: оставил бы я `user_id`?

**Да, оставил бы.** Сервис живёт пользовательскими сценариями, и `user_id`
делает их одношардовыми. Альтернативы хуже для главного:

- `event_id` — локальный JOIN с мероприятиями, но «мои бронирования» разъезжаются
  по всем шардам, а старт продаж на популярный концерт даёт горячий шард ровно в пик;
- id бронирования — идеальный баланс, но ни один пользовательский запрос не знает его заранее;
- `created_at` — вся запись идёт в один «текущий» шард.

Но при проектировании заново я бы сразу добавил:

1. **Копии справочников** на каждом шарде — `events` и `venues`, как в задании 4.
2. **Номер шарда внутри id бронирования** (Snowflake-подобный id), чтобы
   `GET /bookings/{id}` шёл в один шард без scatter-gather.
3. **Колокацию `users`** по тому же `user_id` — JOIN с пользователями станет локальным.
4. **Реплику у каждого шарда** — отказ сервера не лишал бы 22 % пользователей бронирований.
5. **Отдельное хранилище для аналитики** — выручку и отчёты считать там,
   а не scatter-gather'ом по боевым шардам.
6. **Keyset-пагинацию** вместо `OFFSET` во всех списках.
7. **Логические корзины** вместо прямого кольца — для управляемой балансировки
   и возможности вынести горячего пользователя на отдельный сервер.

# Вопросы для самопроверки

### 1. Чем single-shard query отличается от distributed query?

**Single-shard** запрос содержит shard key, поэтому router до выполнения знает
единственный шард с нужными данными: «мои бронирования» — `X-Shards-Queried: 1`.
**Distributed** запрос shard key не содержит и отправляется на все шарды, после чего
бэкенд собирает ответы: выручка, `COUNT`, список всех бронирований — `X-Shards-Queried: 4`.

Разница не только в числе серверов. Распределённый запрос ждёт самого медленного шарда,
ломается при отказе любого из них, требует слияния результатов, а его агрегаты нужно
правильно раскладывать на части.

### 2. Почему JOIN между shard'ами сложнее обычного JOIN?

Обычный JOIN выполняет один сервер над своими таблицами. Между шардами общего сервера
нет: одну сторону соединения приходится везти по сети туда, где лежит другая,
или соединять в приложении. Если бы мероприятия шардировались по `event_id`,
**74 % соединений** оказались бы межсерверными. Решения — копия маленьких
справочников на каждом шарде (416 kB вместо 981 MB бронирований) или колокация
таблиц по одному ключу.

### 3. Как выполнить COUNT(*) по всем shard'ам?

Отправить `SELECT count(*) FROM bookings` на каждый шард параллельно и сложить
результаты на координаторе:
1 101 949 + 1 232 345 + 1 114 852 + 1 550 859 = **5 000 005** — совпадает с primary.
Если хоть один шард недоступен, сумма неверна: сервис отвечает 503, а по явному
`allow_partial=true` возвращает 3 885 153 с пометкой `partial: true`.

### 4. Почему ORDER BY ... LIMIT требует объединения результатов?

Каждый шард знает порядок только своих строк. Самые свежие бронирования разбросаны
по шардам в пропорции 7 : 3 : 3 : 7, а топ-20 одного шарда содержит от 3 до 7 из
настоящего топ-20. Нужно получить топ-N с **каждого** шарда и слить отсортированные
списки: 80 строк → 20, результат совпал с primary. С `OFFSET` каждый шард обязан
вернуть `offset + limit` строк: для страницы 5001 это 400 080 строк ради 20.

### 5. Что произойдёт при отказе одного shard?

При отказе shard-2:

- **11 150 пользователей** (22.3 % данных) потеряли доступ к своим бронированиям:
  503 на чтение, статистику и оформление;
- **остальные 77.7 %** не заметили ничего;
- **все распределённые запросы** — 503, потому что ответ без четверти данных неверен;
- **справочники** на primary работают;
- после восстановления всё вернулось само.

### 6. Что такое hot shard?

Шард, который получает непропорционально большую нагрузку и становится узким местом
всей системы. В эксперименте shard-2 хранил **22 % данных и получал 77 % запросов** —
из-за одного активного пользователя. Причины: неудачный shard key, неравномерное
распределение, популярный пользователь или tenant, тяжёлые типы запросов.

### 7. Почему выбор shard key влияет на JOIN?

JOIN локален, только если связанные строки лежат на одном шарде, а это определяет
shard key. При `user_id` бронирования пользователя и сам пользователь (если `users`
шардировать так же) всегда вместе — JOIN с `users` локальный. Бронирование
и его мероприятие — на одном шарде лишь в **25.58 %** случаев. Сменить ключ на
`event_id` — JOIN с мероприятиями станет локальным, но «мои бронирования»
разъедутся по 4 шардам. Ключ выбирают под самые частые JOIN, остальное решают
копиями справочников.

### 8. Какие операции особенно плохо подходят для распределённых данных?

- JOIN по полю, не являющемуся shard key;
- агрегаты, которые не раскладываются на части: медиана, `COUNT(DISTINCT)`,
  перцентили; «среднее средних» ошибается у 82 % мероприятий;
- глубокая пагинация через `OFFSET` — 400 080 строк ради 20;
- поиск по полю, отличному от shard key, — scatter-gather;
- транзакции, затрагивающие несколько шардов;
- уникальность по всей системе (глобальный `UNIQUE`);
- решардинг, согласованный бэкап и восстановление.

### 9. Что произойдёт при изменении количества shard'ов?

Часть данных придётся переносить (ЛР5). При `hash % N` переход 3 → 4 переносит **75 %**
данных, включая перетасовку между старыми шардами, — 3.75 млн строк. По кольцу —
только долю нового шарда, **31 %**, 1.55 млн строк и только на новый шард.
Во время переноса данные лежат не там, где их ищет router, а общей транзакции
у шардов нет. Поэтому router переключают только после окончания переноса.
Заодно меняется картина нагрузки: сценарии из задания 7 пришлось бы перемерить.

### 10. Чем шардирование отличается от репликации?

| | Репликация (ЛР4) | Шардирование (ЛР5–6) |
|---|---|---|
| Что на каждом сервере | **полная копия** всех данных | **часть** данных |
| Что масштабирует | чтение | чтение **и запись**, и объём |
| `system_identifier` | одинаковый у primary и реплики | разный у каждого шарда |
| Отказ сервера | реплика подменяет primary, данные не теряются | данные шарда недоступны, пока он не вернётся |
| Запросы | любой запрос на любой реплике | зависит от shard key: один шард или все |
| JOIN, агрегаты | работают как обычно | распределённые, требуют слияния |

Они не заменяют, а **дополняют** друг друга: в продакшене у каждого шарда
своя реплика.

### 11. Может ли шардирование сделать отдельный SQL-запрос быстрее?

**Может, но меньше, чем кажется.** Все цифры измерены:

- **Одношардовый запрос** — в БД быстрее: 0.112 мс на шарде против 0.551 мс
  на primary. Таблица меньше, нет обхода 17 партиций. Но в ответе API разницы нет:
  10–12 мс, остальное съедают HTTP и сериализация.
- **Тяжёлый агрегат** — быстрее за счёт параллелизма: 588 мс на 4 шардах против 756 мс
  того же запроса на primary, 1.3×. На отдельных серверах вместо одного компьютера
  было бы ближе к 4×.
- **Кажущееся ускорение в 31 раз** (18 403 мс → 588 мс) почти целиком дала **перестройка
  запроса** («сначала агрегация, потом JOIN»), которую шардирование вынудило сделать.
  На одном primary она даёт те же 24×.
- **Распределённый запрос с глубокой пагинацией** — **медленнее**: 2 455 мс
  на шардах против 91 мс на primary.
- **Лёгкий запрос ко многим шардам** — медленнее из-за цены координации
  и ожидания самого медленного шарда: 29.6 мс при 16 шардах против 14.6 мс при одном.

Шардирование масштабирует **систему** — объём данных, запись, число одновременных
запросов, изоляцию отказов. Отдельный запрос оно ускоряет только когда может разделить
работу между серверами, и замедляет, когда вынуждает их координировать.

# Ограничения

- **Все шарды и primary на одном компьютере.** Параллельные запросы делят процессор
  и диск, поэтому выигрыш от параллелизма занижен (1.3× вместо возможных ~4×),
  а сетевых задержек нет.
- **Шардированный API работает параллельно с основным** (см. ЛР5). Распределённые
  версии реальных запросов добавлены в `/api/shards/...`, основной `/api/bookings`
  по-прежнему работает с primary.
- **Копия справочников обновляется вручную** скриптом — между изменением мероприятия
  и перезаливкой копии на шардах устаревают.
- **Счётчики запросов** в `/api/shards/metrics` хранятся в памяти одного процесса
  uvicorn. При нескольких воркерах нужен общий сбор метрик.
- **Отказ проверен только остановкой контейнера.** Зависший шард — соединение открыто,
  ответа нет — не моделировался: без таймаута на запрос обращение к нему висело бы.
- **Дефект в основном API не исправлен, только зафиксирован:**
  `get_revenue_by_event` выполняется 18.4 с на primary, перестроенный запрос — 0.76 с.
