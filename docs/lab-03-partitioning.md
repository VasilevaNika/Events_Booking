# ЧАСТЬ 1. RANGE PARTITIONING по дате

```sql
CREATE TABLE lab3.events (
    id BIGINT NOT NULL, user_id BIGINT NOT NULL,
    event_type VARCHAR(50) NOT NULL, payload TEXT,
    created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);
```

Три суточные партиции, загружено 900 000 строк.

| Партиция | Границы | Строк | Размер |
|---|---|---|---|
| `events_2026_09_09` | `[2026-09-09 .. 2026-09-10)` | 300 045 | 22 MB |
| `events_2026_09_10` | `[2026-09-10 .. 2026-09-11)` | 300 060 | 22 MB |
| `events_2026_09_11` | `[2026-09-11 .. 2026-09-12)` | 299 895 | 22 MB |

## Ответы на вопросы

### 1. В какую партицию попадёт запись с `created_at = '2026-09-10 12:00:00'`?

**В `lab3.events_2026_09_10`.** Проверено вставкой:

```
 landed_in
------------------------
 lab3.events_2026_09_10
```

Момент попадает в полуинтервал `[2026-09-10 00:00:00, 2026-09-11 00:00:00)`.

### 2. В какую партицию попадёт запись с `created_at = '2026-09-11 00:00:00'`?

**В `lab3.events_2026_09_11`** — то есть в **следующую**, а не в предыдущую.
Проверено вставкой:

```
 landed_in
------------------------
 lab3.events_2026_09_11
```

Это ровно нижняя граница третьей партиции, а `FROM` включается.

### 3. Что произойдёт, если вставить запись за 2026-09-12?

**Вставка упадёт с ошибкой.** Партиции на эту дату нет:

```
ERROR:  no partition of relation "events" found for row
DETAIL:  Partition key of the failing row contains (created_at) = (2026-09-12 10:00:00).
```

Это ключевая эксплуатационная опасность партиционирования по дате: как только
горизонт закончился, приложение начинает падать **на запись**. Именно поэтому
в частях 10–11 делается автоматическое создание партиций и контроль горизонта.

### 4. Почему граница `TO ('2026-09-11')` не включает эту дату?

Потому что PostgreSQL использует **полуинтервал**: `FROM` включительно,
`TO` исключительно — `[FROM, TO)`. Проверка:

```sql
SELECT '2026-09-11 23:59:59.999999'::timestamp < '2026-09-12'::timestamp,  -- t
       '2026-09-12 00:00:00'::timestamp       < '2026-09-12'::timestamp;   -- f
```

```
 fits_09_11 | fits_09_12
------------+------------
 t          | f
```

Причина — так соседние партиции стыкуются **без зазоров и без перекрытий**.
Если бы обе границы включались, значение `2026-09-11 00:00:00` подходило бы
сразу под две партиции, и СУБД не смогла бы выбрать. При полуинтервале
`TO` одной партиции буквально равен `FROM` следующей, и каждое значение
принадлежит ровно одной.

# ЧАСТЬ 2. Partition pruning

## Запрос с ключом партиционирования

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM lab3.events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11';
```

```
Finalize Aggregate  (actual time=25.555..30.020 rows=1 loops=1)
  Buffers: shared hit=2805
  ->  Parallel Seq Scan on events_2026_09_10 events  (actual rows=150030 loops=2)
        Buffers: shared hit=2805
Execution Time: 30.056 ms
```

## Запрос без ключа партиционирования

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM lab3.events WHERE event_type = 'click';
```

```
Finalize Aggregate  (actual time=52.018..56.643 rows=1 loops=1)
  Buffers: shared hit=8413
  ->  Parallel Append  (actual rows=104985 loops=3)
        ->  Parallel Seq Scan on events_2026_09_10 events_2  (Filter: event_type = 'click')
        ->  Parallel Seq Scan on events_2026_09_09 events_1  (Filter: event_type = 'click')
        ->  Parallel Seq Scan on events_2026_09_11 events_3  (Filter: event_type = 'click')
Execution Time: 56.643 ms
```

## Сравнение

| | С ключом | Без ключа |
|---|---|---|
| Узел | одна `Parallel Seq Scan` | **`Parallel Append`** над тремя |
| Партиций в плане | **1 из 3** | **3 из 3** |
| Буферов | **2 805** | **8 413** |
| Время | **30.056 ms** | 56.643 ms |

## Ответы на задание

**Сколько партиций PostgreSQL проверил?** В первом запросе — **одну**.
В плане нет узла `Append`: осталась единственная ветка, две другие отброшены
ещё на этапе планирования.

**Какая партиция действительно нужна запросу?** `events_2026_09_10` — диапазон
условия ровно совпадает с её границами.

**Удалось ли исключить остальные?** Да. Прочитано **2 805 буферов вместо 8 413** —
ровно треть, то есть две партиции не тронуты вовсе.

**Где в плане видно pruning?** Двумя признаками:
1. **отсутствие узла `Append`** — если бы осталась одна ветка из трёх, `Append`
   был бы вырожденным и планировщик его убрал;
2. **имя конкретной партиции прямо в узле** — `Parallel Seq Scan on events_2026_09_10`
   вместо родительской `events`.

> В части 12 на таблице с 17 партициями pruning виден ещё нагляднее —
> отдельной строкой **`Subplans Removed: 16`**.

## Вопрос: почему второй запрос обращается ко всем партициям?

Потому что **`event_type` не является ключом партиционирования**. Таблица
разрезана по `created_at`, и PostgreSQL знает только одно: в какой партиции
какой диапазон дат. Про распределение `event_type` он не знает ничего —
события с `'click'` могут лежать в любой партиции, и в данных они действительно
есть во всех трёх.

Отсечь партицию можно, только если из условия `WHERE` **логически следует**,
что её диапазон значений ключа не пересекается с условием. Для `event_type`
такого вывода сделать нельзя — приходится заглядывать в каждую.

# ЧАСТЬ 3. RANGE PARTITIONING по числовому значению

Партиционирование по `price` тремя диапазонами. Загружено 60 006 товаров.

| Партиция | Границы | Строк |
|---|---|---|
| `products_cheap` | `[0 .. 100)` | 1 177 |
| `products_medium` | `[100 .. 1000)` | 10 653 |
| `products_expensive` | `[1000 .. MAXVALUE)` | 48 176 |

Проверка граничных значений:

| Товар | Цена | Партиция |
|---|---|---|
| Ручка | 49.90 | `products_cheap` |
| Блокнот | **99.99** | `products_cheap` |
| Клавиатура | **100.00** | `products_medium` ← граница |
| Монитор | **999.99** | `products_medium` |
| Ноутбук | **1000.00** | `products_expensive` ← граница |
| Сервер | 250000.00 | `products_expensive` |

Тот же полуинтервал: 99.99 ещё в «дешёвых», ровно 100.00 — уже в «средних».

## Ответ: какие партиции PostgreSQL должен просмотреть для `price >= 100 AND price < 500`?

**Только одну — `products_medium`.** Подтверждено планом:

```
Seq Scan on products_medium products  (actual time=0.005..1.445 rows=4709 loops=1)
Execution Time: 1.586 ms
```

Условие `[100, 500)` целиком вложено в диапазон партиции `[100, 1000)`.
Про `products_cheap` планировщик знает, что там все цены `< 100`, а условие
требует `>= 100` — пересечение пусто. Про `products_expensive` — что там всё
`>= 1000`, а условие требует `< 500`. Обе отсекаются.

Если бы запрос был `price >= 50 AND price < 500`, пришлось бы читать две
партиции: диапазон пересекает границу 100.

# ЧАСТЬ 4. LIST PARTITIONING

Партиционирование `customers` по `customer_type`. 60 000 клиентов.

| Партиция | Значение | Строк |
|---|---|---|
| `customers_b2c` | `'B2C'` | 42 394 |
| `customers_b2b` | `'B2B'` | 16 700 |
| `customers_enterprise` | `'Enterprise'` | 906 |

## Ответы на задание

**Какая партиция используется для `customer_type = 'B2B'`?**
Только `customers_b2b`:

```
Seq Scan on customers_b2b customers  (actual time=0.008..1.842 rows=16700 loops=1)
Execution Time: 2.388 ms
```

Узла `Append` в плане нет — две другие партиции отброшены на этапе планирования.

**Почему PostgreSQL может не обращаться к другим?**
Потому что при LIST-партиционировании каждая партиция объявляет **точный,
исчерпывающий список** значений ключа, которые в ней лежат. Это ограничение
гарантировано самой СУБД: строка с `'B2C'` физически не может оказаться
в `customers_b2b`. Условие `= 'B2B'` совпадает со списком ровно одной партиции,
остальные исключаются логически, без чтения.

**Чем такой сценарий отличается от RANGE?**

| | RANGE | LIST |
|---|---|---|
| Что описывает партиция | непрерывный полуинтервал `[FROM, TO)` | конечный перечень значений |
| Тип ключа | упорядочиваемый (дата, число) | категориальный |
| Отсечение работает для | `=`, `<`, `>`, `BETWEEN` | в основном `=` и `IN` |
| Новое значение ключа | попадает в существующий диапазон, если он покрыт | **не попадает никуда** без новой партиции или DEFAULT |
| Типичное применение | время, суммы, диапазоны id | регион, тип клиента, статус |

Главное практическое различие — в **устойчивости к новым значениям**.
Диапазон `[1000, MAXVALUE)` покрывает любую будущую цену. А список `IN ('B2C','B2B','Enterprise')`
не покрывает ничего сверх перечисленного — что и разбирается в части 5.

# ЧАСТЬ 5. LIST PARTITIONING: неизвестное значение

## Что произошло без DEFAULT-партиции

```sql
INSERT INTO lab3.customers VALUES (100, 'Test User', 'VIP');
```

```
ERROR:  no partition of relation "customers" found for row
DETAIL:  Partition key of the failing row contains (customer_type) = (VIP).
```

## После создания DEFAULT

```sql
CREATE TABLE lab3.customers_default PARTITION OF lab3.customers DEFAULT;
```

Та же вставка проходит, строка попадает в `customers_default`:

```
 id  |   name    | customer_type |    partition_name
-----+-----------+---------------+------------------------
 100 | Test User | VIP           | lab3.customers_default
```

## Ответы на задание

### 1. Зачем нужна DEFAULT partition?

Чтобы **вставка не падала на значении, которого нет ни в одном списке**.
DEFAULT — это «всё остальное»: строки, не подошедшие ни под одну явную партицию,
складываются туда вместо ошибки.

Для LIST это особенно важно: перечень значений задаётся вручную, и любое новое
(новый тип клиента, новый статус, новая страна) без DEFAULT немедленно ломает
запись. Для RANGE роль DEFAULT частично играет диапазон до `MAXVALUE`.

### 2. Чем она полезна?

- **Сервис продолжает работать** при появлении неизвестного значения — ошибка
  вставки в бизнес-таблицу обычно означает отказ пользовательской операции;
- **данные не теряются** — их видно, и потом можно разложить по правильным партициям;
- **страховка от сбоя автоматизации** — если ночная job не создала партицию
  вовремя, DEFAULT примет данные, и авария превратится в предупреждение.
  В миграции `003` для `bookings` DEFAULT создан именно из этих соображений.

### 3. Какие проблемы возникают, если постоянно складывать новые значения в DEFAULT?

**Проблема 1. DEFAULT растёт неограниченно и сводит партиционирование на нет.**
Если 40% строк оседает в DEFAULT, то это просто большая непартиционированная
таблица сбоку, со всеми исходными проблемами.

**Проблема 2. Pruning по DEFAULT почти не работает.** PostgreSQL не знает, какие
значения там лежат — известно лишь, что это «не перечисленные». Любой запрос,
который нельзя однозначно сопоставить с явной партицией, **обязан** заглянуть
в DEFAULT. Она превращается в узел, читаемый почти всегда.

**Проблема 3 — самая неприятная: новую партицию уже не создать.** Проверено:

```sql
CREATE TABLE lab3.customers_vip PARTITION OF lab3.customers FOR VALUES IN ('VIP');
```
```
ERROR:  updated partition constraint for default partition "customers_default"
        would be violated by some row
```

Как только строка с `'VIP'` попала в DEFAULT, завести отдельную партицию для `'VIP'`
нельзя: PostgreSQL пришлось бы проверить, что в DEFAULT нет строк, которые теперь
должны переехать, — и он отказывается. Сначала нужно **вручную перенести**
эти строки, и только потом создавать партицию. На больших объёмах это отдельная
операция с блокировкой.

**Вывод:** DEFAULT — это аварийный клапан, а не место для постоянного хранения.
Правильная эксплуатация: мониторить её наполнение и разбирать содержимое.

# ЧАСТЬ 6. HASH PARTITIONING

Партиционирование `user_events` по `HASH (user_id)` на 4 партиции,
загружено 800 000 строк.

| Партиция | Строк | Доля |
|---|---|---|
| `user_events_0` | 200 566 | **25.07%** |
| `user_events_1` | 200 083 | **25.01%** |
| `user_events_2` | 200 263 | **25.03%** |
| `user_events_3` | 199 088 | **24.89%** |

## Ответы на задание

### 1. Насколько равномерно распределились данные?

**Практически идеально: разброс 24.89–25.07% при теоретических 25%.**
Максимальное отклонение — 0.11 процентного пункта, разница между самой большой
и самой маленькой партицией — 1 478 строк из 800 000 (0.18%).

Это следствие того, что хеш-функция равномерно «размазывает» значения по
остаткам от деления независимо от того, как распределён сам ключ.

### 2. Почему HASH может быть полезен?

- **Гарантированно ровные партиции.** При RANGE по дате всплеск активности
  даёт перекос (data skew): один месяц в разы больше другого. HASH такого
  не допускает по построению.
- **Дробление большой таблицы, когда естественного диапазона нет.** Если
  запросы всегда идут по `user_id`, а делить по времени бессмысленно, HASH
  даёт 4 таблицы по 200 тысяч вместо одной на 800 тысяч.
- **Распараллеливание нагрузки** — партиции можно разнести по разным
  табличным пространствам и дискам.
- **Меньше конкуренции на запись** — вставки расходятся по разным физическим
  файлам вместо одного «горячего конца» таблицы.

Отсечение при поиске по ключу работает:

```
->  Seq Scan on user_events_0 user_events   (Filter: user_id = 12345)
Buffers: shared hit=1475
Execution Time: 9.508 ms
```

Прочитана **одна партиция из четырёх**: 1 475 буферов вместо 5 884.

### 3. Чем HASH отличается от RANGE?

| | RANGE | HASH |
|---|---|---|
| Как определяется партиция | по диапазону значений | по остатку `hash(key) % N` |
| Порядок данных | сохраняется: соседние значения рядом | **полностью теряется** |
| Диапазонные запросы (`BETWEEN`, `>`) | отсекаются отлично | **не отсекаются вообще** |
| Точечный поиск (`=`) | отсекается | отсекается |
| Равномерность | зависит от данных | гарантирована |
| Добавить партицию | просто, новый диапазон | **требует перераспределения** всех данных |
| Удалить старые данные | `DROP TABLE` одной партиции | невозможно адресно |

Обратная сторона видна на том же наборе: поиск по дате не отсекает ничего —

```
->  Parallel Append  (4 партиции)
Buffers: shared hit=5884
Execution Time: 67.527 ms
```

**5 884 буфера против 1 475** при поиске по ключу: в 4 раза больше, вся таблица.

### 4. Почему HASH плохо подходит для «удалить данные старше 3 лет»?

Потому что **строки за любую дату равномерно размазаны по всем партициям**.
Хеш считается от `user_id`, а не от времени, и никакой связи между партицией
и возрастом записи нет.

Последствия:

- **нельзя удалить партицию целиком.** Главная операционная выгода RANGE —
  `DROP TABLE events_2023_01`, мгновенное удаление месяца без `DELETE`,
  без раздувания и без `VACUUM`. Для HASH такой партиции просто не существует:
  в каждой лежат данные за все годы;
- **придётся делать `DELETE ... WHERE created_at < ...`** — по всем четырём
  партициям, с полным сканированием, блокировками, записью в WAL и последующим
  `VACUUM`. То есть ровно та тяжёлая операция, от которой партиционирование
  должно было избавить;
- **место не освобождается сразу** — после `DELETE` файлы остаются прежнего
  размера до `VACUUM FULL`.

Для сценария «жизненный цикл данных по времени» подходит только RANGE по дате.

# ЧАСТЬ 7. Выбор стратегии партиционирования

### Сценарий A — миллионы событий в день, через 3 года удалять старше 3 лет

**RANGE по `created_at`** (шаг — месяц или неделя).

Удаление старых данных превращается в `DROP TABLE events_2023_01` — мгновенную
операцию над метаданными, вместо `DELETE` по миллиардам строк с блокировками
и последующим `VACUUM`. Это главная эксплуатационная выгода RANGE по времени,
и ради неё сценарий и существует.

### Сценарий B — три типа пользователей, запросы фильтруют по типу

**LIST по `customer_type`.**

Значений мало, они фиксированы и категориальны, а 90% запросов содержат
`WHERE customer_type = ?` — то есть pruning будет срабатывать почти всегда.
Обязательно добавить DEFAULT-партицию: появление четвёртого типа иначе
сломает вставку (проверено в части 5).

### Сценарий C — равномерно распределить данные по `user_id`

**HASH по `user_id`.**

Естественного диапазона нет, а нужна именно равномерность — HASH даёт её
по построению (замер части 6: разброс 24.89–25.07%). RANGE по `user_id` дал бы
перекос, потому что старые пользователи активнее новых.

### Сценарий D — заказы, аналитика всегда по `created_at BETWEEN ...`

**RANGE по `created_at`.**

Ключ партиционирования совпадает с тем, что стоит в `WHERE` у основного
потока запросов, поэтому pruning будет работать в большинстве случаев.
Именно этот вариант выбран для `bookings` в части 12 — там один месяц
из семнадцати отсекает 16 партиций.

### Сценарий E — платежи по странам EE, LV, LT, FI, SE

**LIST по коду страны.**

Перечень конечный и стабильный, запросы почти всегда ограничены одной страной.
Дополнительный бонус — требования к хранению данных по юрисдикциям: партиции
можно разнести по разным табличным пространствам. DEFAULT нужна на случай
выхода на новый рынок.

# ЧАСТЬ 8. Партиционирование и индексы

```sql
CREATE INDEX idx_events_user_id ON lab3.events (user_id);
```

## Что физически создалось

| Объект | `relkind` | Тип | Размер |
|---|---|---|---|
| `idx_events_user_id` | `I` | партиционированный (логический) | **0 bytes** |
| `events_2026_09_09_user_id_idx` | `i` | локальный | ~6.6 MB |
| `events_2026_09_10_user_id_idx` | `i` | локальный | ~6.6 MB |
| `events_2026_09_11_user_id_idx` | `i` | локальный | ~6.6 MB |

Индекс на родителе физически **пуст** — это только объявление. Реальные данные
лежат в трёх независимых локальных индексах, по одному на партицию.

## Замер

```sql
SELECT * FROM lab3.events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11'
  AND user_id = 12345;
```

| | План | Буферов | Время |
|---|---|---|---|
| **До индекса** | `Parallel Seq Scan on events_2026_09_10`, `Rows Removed by Filter: 150028` | 2 805 | 20.144 ms |
| **После индекса** | `Bitmap Index Scan on events_2026_09_10_user_id_idx` | **9** | **0.061 ms** |

**В 330 раз быстрее, в 312 раз меньше чтений.**

## Ответы на задание

### 1. Какие партиции отфильтрованы через partition pruning?

Две из трёх: `events_2026_09_09` и `events_2026_09_11`. В плане осталась
единственная ветка `events_2026_09_10`, узла `Append` нет.

### 2. Используется ли индекс?

Да: `Bitmap Index Scan on events_2026_09_10_user_id_idx`, `Index Cond: (user_id = 12345)`.
Узел `Filter` и строка `Rows Removed by Filter` из плана исчезли — отбор
переехал внутрь индекса.

### 3. На каком уровне существует индекс?

**На уровне партиции.** Индекс, созданный на родительской таблице, —
это логический контейнер (`relkind = 'I'`, 0 байт). Физически PostgreSQL
завёл по локальному индексу в каждой партиции и привязал их к родительскому.

Практические следствия:

- **новая партиция получает индекс автоматически.** Это проверено в части 12:
  ночная job создаёт партицию обычным `CREATE TABLE ... PARTITION OF`,
  и все четыре индекса появляются в ней сами;
- **`DROP TABLE` партиции удаляет её индекс вместе с ней** — мгновенно,
  без перестройки чего-либо;
- **каждый локальный индекс маленький.** Дерево на 300 тысяч строк вместо
  дерева на 900 тысяч — ниже высота, лучше шансы удержаться в кэше.

### 4. Почему partitioning + index эффективнее, чем что-то одно?

Потому что **они сокращают разные измерения работы**.

- **Партиционирование режет по горизонтали** — исключает целые куски таблицы
  ещё на этапе планирования, не читая ни байта. Но внутри оставшейся партиции
  оно не помогает: до создания индекса там честно сканировались все 300 тысяч
  строк (`Rows Removed by Filter: 150028` на каждый из двух процессов).
- **Индекс режет по вертикали** — находит нужные строки внутри куска. Но сам
  по себе он не избавляет от необходимости заглянуть в каждую партицию:
  без даты в `WHERE` план вырождается в `Append` по трём локальным индексам.

Вместе получается двухступенчатое сужение: 900 000 строк → 300 000 (pruning)
→ 6 строк (индекс), и на выходе 9 буферов вместо 8 413.

Контрольный замер без ключа партиционирования — тот же поиск по `user_id`,
но без даты:

```
Append  (actual time=0.047..0.088 rows=11 loops=1)
  Buffers: shared hit=14 read=6
  ->  Bitmap Heap Scan on events_2026_09_09 ... (локальный индекс)
  ->  Bitmap Heap Scan on events_2026_09_10 ... (локальный индекс)
  ->  Bitmap Heap Scan on events_2026_09_11 ... (локальный индекс)
```

Индекс работает, но читаются все три партиции — 20 буферов вместо 9.

# ЧАСТЬ 9. Когда партиционирование не помогает

```sql
SELECT COUNT(*) FROM lab3.events WHERE event_type = 'click';
```

| Вариант | План | Буферов | Время |
|---|---|---|---|
| Только партиционирование | `Parallel Append` → 3 × `Seq Scan` + `Filter` | 8 413 | 44.342 ms |
| **+ индекс по `event_type`** | `Parallel Append` → 3 × `Parallel Index Only Scan` | **281** | **23.725 ms** |
| Партиционирование **+** ключ в `WHERE` + индекс | `Bitmap Heap Scan` по одной партиции | 2 896 | 24.854 ms |

Селективность `event_type`:

| Значение | Строк | Доля |
|---|---|---|
| `view` | 351 284 | 39.03% |
| `click` | **314 955** | **34.99%** |
| `login` | 198 559 | 22.06% |
| `purchase` | 35 204 | 3.91% |

## Ответ: почему partitioning сам по себе не решил проблему этого запроса?

**Потому что партиционирование умеет исключать партиции только по своему ключу,
а в запросе его нет.** Таблица разрезана по `created_at`, условие — по `event_type`.
Связи между ними нет: события `'click'` лежат во всех трёх партициях.

В результате вместо одного последовательного сканирования таблицы получилось
**три сканирования** через `Parallel Append` — то есть ровно та же работа плюс
накладные расходы на обход трёх веток плана. Партиционирование здесь не только
не помогло, но и слегка навредило.

Индекс по `event_type` дал 1.9× по времени и **30× по числу буферов** (8 413 → 281),
потому что `Index Only Scan` вообще не ходит в таблицу — `COUNT(*)` считается
по локальным индексам. Это уже работа индекса, а не партиционирования.

Любопытная деталь третьей строки таблицы: комбинация «ключ партиционирования +
индекс» дала 2 896 буферов — **больше**, чем чистый `Index Only Scan` (281).
Причина в селективности: `'click'` — это 35% строк, и выборка внутри одной
партиции всё равно требует поднять треть её страниц из кучи. `Index Only Scan`
же читает только индекс. То есть на низкоселективном условии выгоднее оказался
покрывающий индекс, а не отсечение партиций.

## Вывод: партиционирование отвечает на одну проблему, а индекс — на другую

| | Партиционирование | Индекс |
|---|---|---|
| **Какую задачу решает** | «не читать заведомо ненужные **куски таблицы**» | «не читать заведомо ненужные **строки** внутри куска» |
| **Когда срабатывает** | ключ партиционирования есть в `WHERE` | индексируемая колонка есть в `WHERE` |
| **Что даёт помимо скорости** | мгновенное удаление старых данных, мелкие индексы, быстрый `VACUUM`, обслуживание по частям | ничего, кроме поиска |
| **Чем платим** | метаданные, ограничения на PK и FK, сложность эксплуатации | место на диске, замедление записи |
| **Когда бесполезно** | в `WHERE` нет ключа | низкая селективность, выборка большой доли |

Главный вывод работы: **партиционирование — это в первую очередь инструмент
эксплуатации, а не ускорения запросов.** Запросы оно ускоряет только тогда,
когда ключ партиционирования совпадает с тем, по чему реально фильтруют.
А вот `DROP` старой партиции за миллисекунду вместо многочасового `DELETE`
работает всегда — и обычно именно это оказывается настоящей причиной
переходить на партиции.

# ЧАСТЬ 11. Production-сценарий: ночная job сломалась

## PartitionHealthCheck

Функция `partition_mgmt.health_check()` проверяет, существуют ли все партиции
на горизонте, и возвращает `OK` или `CRITICAL` со списком отсутствующих.

Ключевое решение — **уведомление ставится в очередь только при смене состояния**:

```
OK       -> CRITICAL  =  отправить alert
CRITICAL -> CRITICAL  =  молчать (дедупликация)
CRITICAL -> OK        =  отправить recovery
OK       -> OK        =  молчать
```

## Полный прогон сценария

Выполнено скриптом [`c02_alert_e2e.sh`](../scripts/lab03/c02_alert_e2e.sh)
через HTTP API сервиса.

### Шаг 1. Исходное состояние — OK

```json
  {"table_full_name": "lab3.events",     "check_status": "OK", "missing": [], "notified": false},
  {"table_full_name": "public.bookings", "check_status": "OK", "missing": [], "notified": false}]}
```

### Шаг 2. Искусственно ломаем


### Шаг 3. Проверка обнаруживает проблему

### Шаг 11. Итог

```

----+----------+--------------------------------------------+------+---------------
  1 | CRITICAL | [CRITICAL] Partition alert: lab3.events    | t    |             1
  2 | RECOVERY | [RECOVERY] Partition check OK: lab3.events | t    |             1
```

За весь цикл (5 проверок в состоянии CRITICAL + проверки в OK) отправлено
**ровно два письма**: одно об аварии и одно о восстановлении.

## Почему outbox, а не отправка прямо из проверки

`health_check()` работает внутри СУБД и не умеет ходить в сеть. Кроме того,
если бы отправка шла прямо из функции, недоступность почтового сервера
означала бы **потерю уведомления**. Схема с очередью:

1. `health_check()` в транзакции пишет запись в `partition_alert_outbox`;
2. отдельный процесс (`alert_worker.py` или endpoint API) забирает
   неотправленные записи с `FOR UPDATE SKIP LOCKED` и шлёт их;
3. при ошибке запись остаётся в очереди, растёт `send_attempts`,
   сохраняется `last_error` — следующая попытка подхватит.

`SKIP LOCKED` позволяет запускать несколько воркеров параллельно,
не отправляя одно и то же дважды.

# ЧАСТЬ 12. Партиционирование собственной базы данных

## Шаг 1–3. Таблица, ключ, стратегия

| | Выбор |
|---|---|
| **Таблица** | `public.bookings` |
| **Ключ** | `created_at` |
| **Стратегия** | `RANGE`, шаг — **месяц** |

Реализовано миграцией
[`003_partition_bookings.py`](../migrations/versions/003_partition_bookings.py).

## Шаг 4. Обоснование выбора

### Почему именно эта таблица?

`bookings` — единственная в сервисе таблица без естественного потолка роста.
Это установлено замерами лабораторных №1 и №2: остальные — справочники
(`venues` 200, `events` 2 000, `categories` 20, `users` 50 000), а `bookings`
уже содержит **5 000 000 строк** и растёт как «пользователи × активность × время».

Дополнительный аргумент из ЛР2: на 5 млн строк таблица (355 MB) перестала
помещаться в `shared_buffers` (128 MB), и запрос по диапазону дат стал
деградировать **быстрее, чем растут данные** — ×77 при росте объёма ×50.
Это классический признак, что пора переходить от индексов к партиционированию.

### Почему именно этот ключ?

- `created_at` **есть в `WHERE` основного потока запросов** —
  `GET /api/bookings?from_date=&to_date=` фильтрует именно по нему;
- у данных выраженный **жизненный цикл**: свежие бронирования нужны постоянно,
  прошлогодние — почти никогда. Это позволяет архивировать старое целыми партициями;
- значение **никогда не меняется** после вставки, поэтому строка не «переезжает»
  между партициями;
- распределение **равномерное** — около 425 тысяч строк в месяц, без перекосов.

### Почему именно эта стратегия?

`RANGE` — единственная, дающая главную выгоду для журнальной таблицы:
**`DROP TABLE bookings_2025_09` удаляет месяц данных мгновенно**, вместо
`DELETE FROM bookings WHERE created_at < ...` с блокировками, раздуванием
и многочасовым `VACUUM`.

`LIST` не подходит — дата не категориальна. `HASH` не подходит принципиально:
он размазал бы каждый месяц по всем партициям и сделал бы архивацию невозможной
(разобрано в части 6).

Шаг **месяц**, а не день, выбран осознанно: при суточных партициях за год
накопилось бы 365 таблиц, что раздувает метаданные и замедляет планирование
(о чём предупреждает лекция). Месячный шаг даёт 12–17 партиций по ~425 тысяч
строк — размер, при котором и pruning полезен, и планировщик не страдает.

## Что потребовалось изменить в схеме

Партиционирование наложило два обязательных требования:

**1. `created_at` стал `NOT NULL`** — строку с `NULL`-ключом некуда положить.

**2. Первичный ключ стал составным `(id, created_at)`.** PostgreSQL требует,
чтобы ключ партиционирования входил в любой UNIQUE-индекс: иначе уникальность
пришлось бы проверять сразу во всех партициях. Это ровно то ограничение,
о котором предупреждает лекция, и оно имеет практическое последствие —
см. Запрос 4 ниже.

Модель SQLAlchemy приведена в соответствие, `autoincrement=True` на `id` указан
явно (в составном PK SQLAlchemy по умолчанию отключает автоинкремент).

### Запрос 3 — pruning не работает, и это ожидаемо

```
Merge Append  (actual time=0.585..0.814 rows=50 loops=1)
  Buffers: shared hit=33 read=66
  ->  Index Scan using bookings_2025_09_user_id_created_at_idx ...
  ->  Index Scan using bookings_2025_10_user_id_created_at_idx ...
  ... (все 17 партиций)
```

Строки `Subplans Removed` нет — обходятся **все** партиции. Но запрос всё равно
быстрый (0.974 мс), потому что в каждой работает локальный индекс, а `Merge Append`
использует их отсортированность и останавливается после 50-й строки.

Это тот самый **scatter-gather** из лекции: без ключа партиционирования СУБД
вынуждена заглянуть в каждую партицию.

### Запрос 3-бис — как это чинится

Достаточно добавить разумное ограничение по дате (реальному эндпоинту
«мои бронирования» глубже трёх месяцев обычно и не нужно):

```
Append  (actual time=0.027..0.162 rows=22 loops=1)
  Subplans Removed: 9
  ->  Bitmap Index Scan on bookings_2026_06_user_id_created_at_idx ...
  Buffers: shared hit=34
Execution Time: 0.392 ms
```

**Отсечено 9 партиций, буферов втрое меньше (99 → 34), время вдвое меньше.**

### Запрос 4 — цена составного первичного ключа

```
Append  (actual time=0.360..0.451 rows=1 loops=1)
  Buffers: shared hit=1 read=39
  ->  Index Scan using bookings_2025_09_pkey  (Index Cond: id = 1234567)
  ->  Index Scan using bookings_2025_10_pkey  (Index Cond: id = 1234567)
```

Пока это 40 буферов и полмиллисекунды, но с ростом числа партиций

стоит делать составным (`id` + дата) или включать дату в URL, чтобы эндпоинт
мог отсечь лишнее. Это прямое следствие ограничения на PK, о котором
предупреждает лекция.

# Контрольные вопросы

**1. Что такое partitioning?**
Разделение одной логической таблицы на несколько физических (партиций)
в рамках одного сервера. Для приложения таблица остаётся одной — оно пишет
`SELECT * FROM bookings`, а СУБД сама решает, в какие подтаблицы заглянуть.
В работе `bookings` из одной таблицы на 5 млн строк превратилась в 17 партиций
по ~425 тысяч.

**2. Чем partitioning отличается от индекса?**
Индекс отвечает на вопрос «какие **строки** нужны внутри таблицы»,
партиционирование — «какие **куски таблицы** вообще не нужно открывать».
Отличается и побочная выгода: индекс даёт только скорость поиска, а партиции —
мгновенное удаление старых данных (`DROP TABLE` вместо `DELETE`), мелкие
локальные индексы и обслуживание по частям. Замер части 9: партиционирование
без ключа в `WHERE` не помогло вовсе, а индекс сократил чтения в 30 раз.

**3. Какие стратегии partitioning поддерживает PostgreSQL?**
Три: **RANGE** (диапазоны значений), **LIST** (перечень значений),
**HASH** (остаток от хеша). Плюс `DEFAULT`-партиция для RANGE и LIST
и возможность вложенного партиционирования (партиция сама партиционирована).

**4. Когда использовать RANGE?**
Когда ключ упорядочен и у данных есть жизненный цикл: время, суммы, диапазоны
идентификаторов. Идеальный случай — журналы, история транзакций, аудит,
метрики. Главный признак: нужно уметь массово удалять или архивировать старое.

**5. Когда использовать LIST?**
Когда ключ категориальный с конечным перечнем: регион, страна, тип клиента,
статус. Основные запросы должны фильтровать по этому признаку. Обязательно
добавлять DEFAULT — иначе появление нового значения ломает вставку.

**6. Когда использовать HASH?**
Когда естественного диапазона или списка нет, а нужно просто равномерно
разбить большую таблицу — обычно по `user_id`. Замер части 6: разброс
24.89–25.07% при теоретических 25%. Не подходит, если данные нужно удалять
по времени.

**7. Как выбрать partition key?**
Четыре критерия, применённые при выборе `created_at` для `bookings`:
он **присутствует в `WHERE` основного потока запросов** (иначе pruning
не сработает никогда); он **не меняется** после вставки (иначе строка
«переезжает»); он даёт **равномерное распределение** (без перекоса);
по нему **осмысленно удалять данные целыми партициями**.

**8. Что такое partition pruning?**
Исключение партиций из плана запроса на основании условия `WHERE`.
В плане видно двумя способами: отдельной строкой **`Subplans Removed: N`**
(часть 12, 16 из 17 партиций) или **отсутствием узла `Append`** и именем
конкретной партиции в узле сканирования (часть 2).

**9. Почему pruning может не сработать?**
Основная причина — **ключа партиционирования нет в `WHERE`**. Замеры:
поиск по `event_type` при партиционировании по `created_at` (часть 9) и
`GET /api/users/{id}/bookings` без даты (часть 12, обходятся все 17 партиций).
Другие причины: функция над ключом (`DATE(created_at) = ...`), условие на ключ
через `OR` с неключевой колонкой, значение ключа неизвестно на этапе
планирования (тогда возможен более слабый runtime pruning), и наличие
DEFAULT-партиции — её приходится проверять почти всегда.

**10. Можно ли использовать индексы вместе с partitioning?**
Да, и это основной сценарий. `CREATE INDEX` на родительской таблице создаёт
логический индекс (`relkind = 'I'`, **0 байт**) и по локальному физическому
индексу в каждой партиции. Новая партиция получает индексы автоматически.
Замер части 8: pruning + локальный индекс дали 20.144 → 0.061 мс, в 330 раз.

**11. Что произойдёт, если подходящей партиции нет?**
Вставка упадёт: `ERROR: no partition of relation "events" found for row`.
Это не предупреждение, а отказ операции — то есть падение пользовательского
сценария. Страховка: `DEFAULT`-партиция (принимает такие строки) и
автоматическое создание партиций заранее.

**12. Зачем создавать будущие партиции заранее?**
Потому что партиция нужна **в момент вставки**, а не потом. Если ждать
наступления новых суток, между полуночью и созданием партиции все `INSERT`
будут падать. Горизонт (в работе — 3 шага вперёд) даёт запас: даже если job
не отработает одну-две ночи, сервис продолжит писать, а проблему успеют заметить.

**13. Почему создание партиций должно быть автоматизировано?**
Потому что это регулярная операция, забыть которую — значит уронить запись
в продакшене. Человек не может надёжно создавать партицию каждую ночь.
В работе автоматизация сделана на `pg_cron` внутри СУБД: задание переживает
перезапуск приложения, не требует отдельного контейнера и выполняется один раз
даже при нескольких репликах бэкенда.

**14. Чем логирование ошибки отличается от alerting?**
Лог **пассивен**: запись появляется, но её надо пойти и прочитать. Alert
**активен**: он сам приходит к дежурному. Разница критична для сценария
этой лабораторной — если о том, что партиция не создана, узнают из лога
только утром, приложение уже несколько часов как падает на `INSERT`.
В работе есть и то и другое: `partition_job_log` (журнал) и письмо (alert).

**15. Что такое recovery alert?**
Уведомление о том, что проблема **устранена**. Без него дежурный, получивший
`CRITICAL`, не знает, чинилось ли что-то, и вынужден проверять вручную.
В работе recovery отправляется при переходе `CRITICAL → OK`:
`🟢 Partition check OK ... All required partitions exist.`

**16. Почему нельзя бесконечно отправлять одинаковый alert?**
Потому что канал превращается в шум, и на него перестают реагировать
(alert fatigue). При проверке каждые 5 минут одна незакрытая проблема
дала бы 288 писем в сутки. В работе уведомление ставится в очередь только
при **смене состояния**: за 5 проверок в состоянии CRITICAL отправлено
**одно** письмо, повторные обнаружения только увеличили `check_count`.

**17. Всегда ли partitioning ускоряет запросы?**
Нет. Если ключа партиционирования нет в `WHERE`, вместо одного сканирования
получается `Append` по всем партициям — то есть та же работа плюс накладные
расходы. Замер части 9: `COUNT(*) WHERE event_type = 'click'` при
партиционировании по дате дал `Parallel Append` по трём партициям,
8 413 буферов, 44.342 мс — быстрее не стало. Более того, в части 12
`GET /api/bookings/{id}` стал обходить все 17 партиций из-за составного
первичного ключа.

**18. Какие проблемы возникают при неправильном выборе размера партиций?**

*Слишком мелкие (например, суточные на несколько лет):*
- **раздувание метаданных** — каждая партиция это отдельные файлы, строки
  в системных каталогах и локальные индексы;
- **рост времени планирования** — планировщик анализирует сотни подтаблиц
  на каждый запрос, и для коротких запросов планирование становится дороже
  выполнения;
- запрос за широкий диапазон собирает десятки веток `Append`.

*Слишком крупные (например, годовые при 5 млн записей в месяц):*
- **pruning почти не даёт выгоды** — отсечь можно только целый год;
- **партиция не помещается в кэш**, то есть исходная проблема возвращается;
- **удаление данных теряет гранулярность** — нельзя удалить «старше 3 месяцев»,
  только «старше года».

Именно поэтому для `bookings` выбран **месячный** шаг: 17 партиций
по ~425 тысяч строк (~30 MB heap). Суточные дали бы 365+ таблиц в год,
годовые — партиции по 5 млн строк, то есть ровно то состояние, из которого
уходили.

# Общие выводы

1. **Partition pruning работает только по ключу партиционирования.** Замеры:
   с ключом — 1 партиция из 17 и `Subplans Removed: 16`; без ключа —
   все 17 через `Append`. Это главный критерий выбора ключа: он должен совпадать
   с тем, по чему реально фильтруют.

2. **Партиционирование — инструмент эксплуатации, а не только скорости.**
   Ускорение запросов условно (часть 9: без ключа в `WHERE` стало даже чуть
   хуже), а вот `DROP TABLE bookings_2025_09` вместо `DELETE` по 266 тысячам
   строк работает всегда и мгновенно.

3. **Границы — полуинтервал `[FROM, TO)`.** Проверено на обеих RANGE-таблицах:
   `2026-09-11 00:00:00` попадает в следующую партицию, цена ровно `100.00` —
   в «средние», а не в «дешёвые». Так партиции стыкуются без зазоров и перекрытий.

4. **Индексы в партиционированной таблице — локальные.** Родительский индекс
   весит 0 байт и является объявлением; физические индексы живут в партициях,
   создаются для новых партиций автоматически и удаляются вместе с ними.
   Комбинация pruning + локальный индекс дала 20.144 → 0.061 мс (в 330 раз).

5. **Партиционирование и индексы решают разные задачи.** Первое режет по
   горизонтали (какие куски таблицы не открывать), второе — по вертикали
   (какие строки внутри куска не читать). В части 8 они сработали вместе:
   900 000 строк → 300 000 → 6, и 9 буферов вместо 8 413.

6. **DEFAULT-партиция — аварийный клапан, а не хранилище.** Она спасает
   вставку от падения, но ломает pruning и, что важнее, **блокирует создание
   нормальной партиции** для значения, которое уже в неё попало
   (`ERROR: updated partition constraint ... would be violated`).

7. **HASH даёт идеальную равномерность ценой потери порядка.** 24.89–25.07%
   при теоретических 25%, но поиск по дате не отсекает ни одной партиции,
   а «удалить старше 3 лет» становится невозможным адресно.

8. **Партиционирование меняет схему, и за это приходится платить.**
   `created_at` стал `NOT NULL`, первичный ключ — составным `(id, created_at)`.
   Прямое следствие: `GET /api/bookings/{id}` теперь обходит все 17 партиций.
   Это не дефект реализации, а фундаментальное ограничение PostgreSQL.

9. **Без автоматизации партиционирование опасно.** Как только горизонт
   заканчивается, приложение падает **на запись**:
   `ERROR: no partition of relation "events" found for row`. Поэтому рабочая
   система — это не `PARTITION BY RANGE`, а связка «ночная job + проверка
   горизонта + alert + recovery», и все четыре звена в работе реализованы
   и проверены искусственным сбоем.

10. **Alert без дедупликации бесполезен.** При проверке каждые 5 минут
    незакрытая проблема дала бы 288 писем в сутки, и на них перестали бы
    реагировать. Уведомление по смене состояния даёт ровно два письма
    на инцидент: авария и восстановление.
