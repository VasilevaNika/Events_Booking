# Лабораторная работа №1. Индексы и EXPLAIN ANALYZE в PostgreSQL

**Сервис:** Booking Service API (FastAPI + SQLAlchemy + PostgreSQL) — сервис бронирования мероприятий.
**СУБД:** PostgreSQL 16.15 (Debian, контейнер `booking_postgres`).
**Дата выполнения:** 10.09.2026.

Главное правило работы соблюдено: **ни один индекс не считается полезным без измерения**.
Каждое изменение подтверждено парой `EXPLAIN ANALYZE` «до» и «после».

## Параметры окружения

Их важно зафиксировать, потому что от них напрямую зависит выбор плана:

| Параметр | Значение |
|---|---|
| `shared_buffers` | 16384 (128 MB) |
| `effective_cache_size` | 524288 (4 GB) |
| `work_mem` | 4096 (4 MB) |
| `seq_page_cost` | 1 |
| `random_page_cost` | 4 |
| `max_parallel_workers_per_gather` | 2 |
| `min_parallel_table_scan_size` | 1024 (8 MB) |

Все таблицы целиком помещаются в кэш (`Buffers: shared hit=...` почти везде), поэтому
абсолютные времена малы, но **соотношения** между планами показательны.

## Задание 3. EXPLAIN

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
```

```
Gather  (cost=1000.00..17036.43 rows=11 width=53)
  Workers Planned: 2
  ->  Parallel Seq Scan on orders  (cost=0.00..16035.33 rows=5 width=53)
        Filter: (user_id = 123)
```

**1. Какой план выполнения выбрал PostgreSQL?**
Параллельное последовательное сканирование: `Gather` над `Parallel Seq Scan` с двумя
рабочими процессами. Оценочная стоимость — 17036 условных единиц.

**2. Какой тип сканирования используется?**
`Parallel Seq Scan` — последовательное чтение всей таблицы, разделённое между тремя
процессами (лидер + 2 воркера). Индекса по `user_id` в этот момент ещё не существует,
единственный индекс в таблице — `orders_pkey` по `id`, и для условия по `user_id` он бесполезен.

**3. Как PostgreSQL планирует найти необходимые строки?**
Прочитать все 10 827 страниц таблицы, к каждой строке применить `Filter: (user_id = 123)`
и отбросить всё, что не подошло. Планировщик ожидает `rows=11` на выходе — это оценка,
полученная из статистики: 1 000 000 / 91 762 ≈ 11.

Обратите внимание: `cost` начинается не с 0.00, а с **1000.00** — это `parallel_setup_cost`,
плата за запуск воркеров.

## Задание 4. EXPLAIN ANALYZE

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 123;
```

Прогон 1 (холодный):
```
Gather  (cost=1000.00..17036.43 rows=11 width=53) (actual time=7.962..42.546 rows=6 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  Buffers: shared hit=10827
  ->  Parallel Seq Scan on orders  (actual time=14.567..34.457 rows=2 loops=3)
        Filter: (user_id = 123)
        Rows Removed by Filter: 333331
        Buffers: shared hit=10827
Planning Time: 0.056 ms
Execution Time: 42.578 ms
```

Прогон 2 (тёплый кэш): **Execution Time: 27.587 ms**.

### Что найдено в плане

| Метрика | Значение |
|---|---|
| Тип сканирования | `Parallel Seq Scan` |
| `Planning Time` | 0.056 мс |
| `Execution Time` | 27.587 мс (тёплый прогон) |
| `actual rows` | **6** (на верхнем узле `Gather`) |
| `Rows Removed by Filter` | **333 331 на каждый из 3 процессов** ≈ 999 994 суммарно |
| `Buffers` | `shared hit=10827` — прочитаны все страницы таблицы |

Ключевая деталь: у `Parallel Seq Scan` указано `rows=2 loops=3`. Это значит «в среднем
2 строки за проход, проходов было 3». Реальное суммарное число — 2 × 3 = 6, что и видно
на `Gather`. То же правило действует и для `Rows Removed by Filter`.

**1. Чем EXPLAIN отличается от EXPLAIN ANALYZE?**
`EXPLAIN` только строит план на основе статистики и **не выполняет запрос** — показывает
лишь ожидания планировщика (`cost`, `rows`, `width`). `EXPLAIN ANALYZE` **реально выполняет**
запрос и добавляет фактические данные: `actual time`, `actual rows`, `loops`,
`Rows Removed by Filter`, а с опцией `BUFFERS` — ещё и статистику чтения страниц.

Практическое следствие по технике безопасности: `EXPLAIN ANALYZE` на `INSERT`/`UPDATE`/`DELETE`
**реально изменит данные**. Чтобы этого избежать, такой запрос нужно оборачивать в
`BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`.

**2. Почему EXPLAIN ANALYZE может выполняться значительно дольше?**
Потому что он тратит ровно столько времени, сколько занимает сам запрос, плюс накладные
расходы на инструментирование: перед каждой строкой и после неё вызывается системный таймер.
На планах с миллионами строк и глубокой вложенностью узлов эти замеры сами по себе заметны
(эффект известен как *timing overhead*; его можно исключить через `EXPLAIN (ANALYZE, TIMING OFF)`).
`EXPLAIN` же отрабатывает за доли миллисекунды — здесь 0.056 мс против 27.587 мс, разница ~500×.

**3. Чем отличаются estimated и actual значения количества строк?**
`estimated` (`rows=11`) — предсказание планировщика по статистике из `pg_statistic`;
`actual` (`rows=6`) — сколько строк реально прошло через узел. Здесь оценка завышена почти
вдвое, но это нормально: PostgreSQL считал 1 000 000 / 91 762 ≈ 11, а у конкретного
`user_id = 123` оказалось 6 заказов — случайное отклонение.

Важно то, что расхождение **невелико**. Если бы разрыв был на порядки (например,
`rows=1` против `actual rows=500000`), это был бы сигнал устаревшей статистики или
коррелированных условий — и почти наверняка привело бы к выбору неверного плана.

## Задание 5. Sequential Scan

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders;
```
```
Seq Scan on orders  (cost=0.00..20827.00 rows=1000000 width=53)
                    (actual time=0.010..54.676 rows=1000000 loops=1)
  Buffers: shared hit=10827
Execution Time: 83.496 ms
```

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE amount > 0;
```
```
Seq Scan on orders  (cost=0.00..23327.00 rows=999900 width=53)
                    (actual time=0.010..116.181 rows=1000000 loops=1)
  Filter: (amount > '0'::numeric)
  Buffers: shared hit=10827
Execution Time: 144.725 ms
```

Проверка: `SELECT count(*) FROM orders WHERE amount > 0` → **1 000 000 из 1 000 000**, то есть
условие не отсекает ничего.

**1. Какой тип сканирования используется?**
`Seq Scan` в обоих случаях. Причём здесь он даже не параллельный: для запроса без `WHERE`
параллелизм не даёт выигрыша, так как все строки всё равно нужно передать наверх.

**2. Почему PostgreSQL выбирает Sequential Scan?**
- В первом запросе `WHERE` вообще нет — нужны все строки, любой индекс был бы лишним звеном.
- Во втором запросе условие `amount > 0` истинно для 100% строк. Планировщик оценил
  `rows=999900` (99.99%) и понял: поход в индекс за адресами всех строк, а затем чтение
  всей таблицы обойдётся дороже, чем сразу прочитать таблицу подряд.

Разница в `cost` наглядна: 20827 против 23327. Лишние 2500 единиц — это `cpu_operator_cost`
на вычисление `amount > 0` для каждой из миллиона строк. Это же видно и по времени:
83 мс против 145 мс — фильтр, который ничего не фильтрует, стоит 60 мс чистого CPU.

**3. Всегда ли Sequential Scan является плохим решением?**
Нет. `Seq Scan` — это **последовательное** чтение с диска, самый дружественный к железу
паттерн доступа (`seq_page_cost = 1` против `random_page_cost = 4`, то есть в модели
планировщика случайное чтение вчетверо дороже). Index Scan вместо этого делает «прыжки»
по случайным адресам. Когда нужных строк много, эти прыжки становятся дороже честного
чтения всей таблицы.

### Вывод: когда Seq Scan эффективнее индекса

1. **Запрос возвращает большую долю таблицы.** Практический порог для PostgreSQL —
   примерно **5–20%**. Ниже по тексту (задание 9) это подтверждено экспериментально:
   при 25% выбирается Bitmap Scan, при 50% — уже чистый `Seq Scan`.
2. **Таблица маленькая.** Несколько страниц дешевле прочитать целиком, чем открывать индекс.
3. **Нужны все или почти все колонки всех строк** — например, выгрузка или аналитика.
4. **Отсутствует подходящий индекс**, а разовый запрос не оправдывает его создание.
5. **Условие не индексируемо**: функция над колонкой без expression-индекса (задание 18),
   `LIKE '%...'` с ведущим `%`, приведение типов.

## Задание 6. Первый B-tree индекс

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);   -- 9088 kB
ANALYZE orders;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 123;
```

```
Bitmap Heap Scan on orders  (cost=4.51..47.60 rows=11 width=53)
                            (actual time=0.020..0.029 rows=6 loops=1)
  Recheck Cond: (user_id = 123)
  Heap Blocks: exact=6
  Buffers: shared hit=9
  ->  Bitmap Index Scan on idx_orders_user_id  (cost=0.00..4.51 rows=11 width=0)
                                               (actual time=0.015..0.015 rows=6 loops=1)
        Index Cond: (user_id = 123)
        Buffers: shared hit=3
Planning Time: 0.068 ms
Execution Time: 0.046 ms
```

### Сравнительная таблица

| Метрика | До индекса | После индекса | Изменение |
|---|---|---|---|
| Тип Scan | `Parallel Seq Scan` | `Bitmap Index Scan` + `Bitmap Heap Scan` | — |
| `Execution Time` | 27.587 мс | **0.046 мс** | **в 600 раз быстрее** |
| Прочитано страниц (`Buffers`) | 10 827 | **9** | **в 1203 раза меньше** |
| Обработано строк | 1 000 000 (из них 999 994 отброшено фильтром) | **6** (ничего не отбрасывается) | — |
| Используемый индекс | нет | `idx_orders_user_id` | — |
| `cost` | 17036.43 | 47.60 | в 358 раз ниже |

**1. Изменился ли план выполнения?**
Да, кардинально. Вместо чтения всех 10 827 страниц тремя параллельными процессами
PostgreSQL читает 3 страницы индекса, получает из них 6 адресов строк (TID) и точечно
поднимает **6 страниц** таблицы (`Heap Blocks: exact=6`). Параллелизм исчез за ненадобностью.

Исчез и `Rows Removed by Filter` — вместо `Filter` теперь `Index Cond`. Это принципиальная
разница: `Filter` применяется к строкам **после** их чтения, а `Index Cond` ограничивает
диапазон обхода дерева, то есть лишние строки вообще не читаются.

**2. Использует ли PostgreSQL созданный индекс?**
Да. Причём выбран не `Index Scan`, а связка `Bitmap Index Scan` → `Bitmap Heap Scan`.
Для 6–11 строк, разбросанных по разным страницам, bitmap-подход выгоднее: он собирает
все адреса, сортирует их по номеру страницы и читает страницы **по возрастанию**,
превращая случайные чтения в почти последовательные.

**3. Насколько изменилось время выполнения?**
27.587 мс → 0.046 мс, то есть **в 600 раз**. И это на «тёплом» кэше, где вся таблица уже
лежит в памяти. На реальной базе, которая не помещается в `shared_buffers`, разрыв был бы
ещё больше: Seq Scan упирался бы в диск, а индексный доступ — нет.

Цена вопроса: индекс занял 9088 kB (около 10% от размера таблицы) и замедлил запись
(измерено в задании 19).

## Задание 7. Индекс и низкая селективность

```sql
CREATE INDEX idx_orders_status ON orders(status);  -- 6848 kB
```

| Значение | Строк | % таблицы | Выбранный план | `Execution Time` | `Heap Blocks` |
|---|---|---|---|---|---|
| `PAID` | 249 807 | 24.98% | Bitmap Heap Scan | 51.605 мс | **exact=10827** |
| `NEW` | 250 663 | 25.07% | Bitmap Heap Scan | 51.074 мс | **exact=10827** |
| `DELIVERED` | 250 037 | 25.00% | Bitmap Heap Scan | 53.676 мс | **exact=10827** |
| `CANCELLED` | 249 493 | 24.95% | Bitmap Heap Scan | 52.171 мс | **exact=10827** |

**1. Во всех ли случаях PostgreSQL использует индекс?**
На четырёх «ровных» значениях по 25% — формально да, индекс используется. Но результат
обманчив, и это самое поучительное место работы: **`Heap Blocks: exact=10827` означает,
что прочитаны все до единой страницы таблицы**. Индекс не сэкономил ни одного чтения —
он лишь добавил к полному сканированию таблицы ещё 213 страниц самого индекса.

Такой план называют *вырожденным*: формально это индексный доступ, фактически —
последовательное чтение с накладными расходами сверху.

Стоит расширить условие — и индекс отбрасывается совсем:

| Условие | Доля таблицы | План | Время |
|---|---|---|---|
| `status = 'PAID'` | 25% | Bitmap Heap Scan | 51.6 мс |
| `status IN ('PAID','NEW')` | 50% | Bitmap Heap Scan | 76.3 мс |
| `status <> 'NEW'` | 75% | **Seq Scan** | 115.4 мс |
| `status IS NOT NULL` | 100% | **Seq Scan** | 116.8 мс |

**2. Почему PostgreSQL может выбрать Seq Scan, несмотря на наличие индекса?**
Планировщик сравнивает стоимости, а не «наличие индекса». Проверим прямым экспериментом —
запретим индексные методы и заставим тот же запрос идти через `Seq Scan`:

```
SET enable_bitmapscan = off; SET enable_indexscan = off;
Seq Scan on orders (cost=0.00..23327.00 rows=246300) (actual ... rows=249807)
  Filter: ((status)::text = 'PAID'::text)
  Rows Removed by Filter: 750193
Execution Time: 94.923 ms
```

Итог: bitmap-план — 51.6 мс при `cost=16659`, seq-план — 94.9 мс при `cost=23327`.
Планировщик выбрал дешевле, и по факту оказался прав (51.6 < 94.9). А вот при 75%
(`status <> 'NEW'`) стоимость bitmap-плана уже превысила `Seq Scan`, и он был отвергнут.

Причины, по которым индекс проигрывает:
- **Низкая селективность:** 4 различных значения на миллион строк.
- **Random I/O:** 250 000 обращений по случайным адресам дороже 10 827 последовательных чтений.
- **Двойная работа:** нужно прочитать и индекс, и всё равно всю таблицу.
- **Плохая корреляция:** `correlation` для `status` = 0.245 — строки одного статуса физически
  «размазаны» по всей таблице, а не лежат рядом.

**3. Как количество возвращаемых строк влияет на выбор плана?**
Прямо и решающе. Наглядный контрпример из той же таблицы с тем же объёмом данных:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE id = 500000;
```
```
Index Scan using orders_pkey on orders  (actual time=0.028..0.030 rows=1 loops=1)
  Index Cond: (id = 500000)
  Buffers: shared hit=4
Execution Time: 0.050 ms
```

1 строка → `Index Scan`, 4 страницы, 0.050 мс.
250 000 строк → вырожденный Bitmap, 11 040 страниц, 51.6 мс.
**Разница в 1000 раз при одинаковой таблице и одинаковом наличии индексов.**

## Задание 8. Селективность

```sql
SELECT status, count(*) FROM orders GROUP BY status;
```

| `status` | Строк | % таблицы | Селективность условия | Используется индекс | Тип Scan |
|---|---|---|---|---|---|
| `NEW` | 250 663 | 25.07% | 0.2507 | формально да, фактически бесполезен | Bitmap Heap Scan (все 10827 страниц) |
| `DELIVERED` | 250 037 | 25.00% | 0.2500 | то же | Bitmap Heap Scan |
| `PAID` | 249 807 | 24.98% | 0.2498 | то же | Bitmap Heap Scan |
| `CANCELLED` | 249 493 | 24.95% | 0.2495 | то же | Bitmap Heap Scan |

Селективность колонки по формуле из лекции: `n_distinct / общее число строк` = 4 / 1 000 000
= **0.000004** — предельно низкая.

### Вывод: как селективность влияет на эффективность индекса

Индекс полезен ровно настолько, насколько он **сокращает объём чтения**. Мера этого —
селективность условия (доля возвращаемых строк).

Сводная шкала, полученная измерениями в этой работе:

| Доля таблицы | План | Эффект индекса | Пример из работы |
|---|---|---|---|
| ~0.0001% (1 строка) | `Index Scan` | максимальный, 4 страницы | `id = 500000`, 0.050 мс |
| 0.14% | `Bitmap Heap Scan` | отличный, 1306 страниц | `created_at > NOW() - 1 day`, 3.2 мс |
| ~1% | `Bitmap Heap Scan` | хороший, 6528 страниц | `created_at > NOW() - 7 days`, 17.1 мс |
| 4% | `Bitmap Heap Scan` | умеренный, 10 671 страница | `created_at > NOW() - 1 month`, 40.5 мс |
| 25% | `Bitmap Heap Scan` | **нулевой**, читается вся таблица | `status = 'PAID'`, 51.6 мс |
| 50%+ | `Seq Scan` | индекс отброшен планировщиком | `created_at > NOW() - 1 year`, 357 мс |

Практические следствия:

1. **Индекс по колонке-перечислению (`status`, `is_active`, `gender`) сам по себе почти
   бесполезен.** Он занимает место и тормозит запись, не ускоряя чтение.
2. **Такую колонку нужно делать не отдельным индексом, а первой колонкой составного** —
   тогда она сужает диапазон, а сортировку внутри обеспечивает вторая колонка
   (см. задания 12 и 21, и именно так сделано в миграции сервиса).
3. **Либо использовать частичный индекс** — если интересует редкое значение (задание 17).
4. Важна не селективность колонки вообще, а селективность **конкретного условия**:
   `created_at` почти уникальна, но `created_at > NOW() - 1 year` возвращает половину

```
Gather  (cost=1000.00..20027.37 rows=9087) (actual time=0.712..128.220 rows=9822)
  ->  Parallel Seq Scan on orders

```

### Исследование разных диапазонов

| Диапазон | Строк | % таблицы | Тип Scan | `Heap Blocks` | `Execution Time` |
|---|---|---|---|---|---|
| 1 день | 1 378 | 0.14% | Bitmap Heap Scan | 1 299 | **3.239 мс** |
| 7 дней | 9 822 | 0.98% | Bitmap Heap Scan | 6 522 | 17.098 мс |
| 1 месяц | 42 010 | 4.20% | Bitmap Heap Scan | 10 641 | 40.477 мс |
| 6 месяцев | 249 979 | 25.00% | Bitmap Heap Scan | **10 827** | 145.842 мс |
| 1 год | 500 049 | 50.00% | **Seq Scan** | — | **357.430 мс** |

**1. Во всех ли случаях PostgreSQL использует индекс?**
Нет. До 25% включительно выбирается Bitmap Scan, а на 50% планировщик полностью
отказывается от индекса в пользу `Seq Scan`.

**2. Как размер временного диапазона влияет на план выполнения?**
Монотонно и предсказуемо. Ключевой показатель — не время, а **`Heap Blocks`**:

- 1 день → 1 299 страниц из 10 827 (12% таблицы) — индекс экономит 88% чтений;
- 1 месяц → 10 641 страница (98%) — экономия почти исчезла;
- 6 месяцев → 10 827 (100%) — **экономии нет вообще**, читается вся таблица плюс индекс.

Причина «схлопывания» — низкая физическая корреляция: `correlation` для `created_at`
равна −0.0043, то есть даты сгенерированы случайно и не упорядочены на диске. Уже
42 000 случайно разбросанных строк «задевают» почти каждую страницу таблицы. Если бы
данные были вставлены по возрастанию `created_at` (как в реальном логе событий),
корреляция была бы близка к 1, и индекс работал бы куда дольше — а для таких случаев
существует BRIN.

**3. В какой ситуации использование индекса становится менее выгодным?**
Когда число целевых строк приближается к числу страниц таблицы. Здесь таблица занимает
10 827 страниц, и уже при ~42 000 строк (4%) индекс перестаёт что-либо экономить.
Отсюда практическое правило: **выгода индекса определяется не долей строк, а долей
затронутых страниц**, а она зависит от корреляции.

## Задание 10. Bitmap Scan

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE amount BETWEEN 1000 AND 3000;
```

Без индекса по `amount`: `Seq Scan`, 264.177 мс.

После `CREATE INDEX idx_orders_amount ON orders(amount)`:
```
Bitmap Heap Scan on orders  (cost=4189.03..17973.01 rows=197132) (actual time=55.437..104.504 rows=199934)
  Recheck Cond: ((amount >= '1000'::numeric) AND (amount <= '3000'::numeric))
  Heap Blocks: exact=10827
  ->  Bitmap Index Scan on idx_orders_amount  (actual time=53.384..53.385 rows=199934)
        Index Cond: ((amount >= '1000'::numeric) AND (amount <= '3000'::numeric))
Execution Time: 114.521 ms
```

Требуемая структура плана получена. Более удачный пример — среднеселективный запрос,
где bitmap действительно экономит:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id BETWEEN 100 AND 400;
```
```
Bitmap Heap Scan on orders  (actual time=0.843..4.121 rows=2923 loops=1)
  Heap Blocks: exact=2564
  ->  Bitmap Index Scan on idx_orders_user_id  (actual time=0.421..0.422 rows=2923)
Execution Time: 4.296 ms
```
2 923 строки (0.29%) → 2 564 страницы вместо 10 827.

**1. Что делает Bitmap Index Scan?**
Обходит индекс по условию и вместо того, чтобы сразу идти за каждой строкой в таблицу,
**строит в памяти битовую карту** — набор отметок «в такой-то странице есть нужные строки».
На выходе узла `rows=2923`, но `Buffers` этого узла — всего 5–9 страниц: он читает
только индекс. Заметьте, у этого узла `width=0` — он не извлекает данные, только адреса.

Если строк слишком много и карта не помещается в `work_mem`, PostgreSQL переходит на
*lossy*-режим: запоминает только номера страниц без позиций внутри них. Тогда в
`Bitmap Heap Scan` появляется `Rows Removed by Index Recheck`.

**2. Что делает Bitmap Heap Scan?**
Берёт готовую битовую карту и читает отмеченные страницы таблицы **строго по возрастанию
номера**. Это и есть главный выигрыш: случайные обращения превращаются в последовательный
проход, дружественный к упреждающему чтению. `Heap Blocks: exact=2564` — сколько страниц
реально прочитано. `Recheck Cond` нужен на случай lossy-режима: для страниц, отмеченных
целиком, условие перепроверяется на каждой строке.

**3. Почему PostgreSQL может использовать Bitmap Scan вместо обычного Index Scan?**

| | `Index Scan` | `Bitmap Scan` |
|---|---|---|
| Порядок чтения таблицы | в порядке индекса (случайный по диску) | по возрастанию номера страницы |
| Одна страница с 5 нужными строками | прочитана до 5 раз | прочитана **один раз** |
| Сохраняет сортировку индекса | **да** | **нет** |
| Можно объединять индексы | нет | **да** (`BitmapAnd` / `BitmapOr`) |
| Оптимален при | 1–несколько строк, либо нужен `ORDER BY` | десятки–сотни тысяч строк |

Bitmap выбирается, когда строк «средне много»: обычный `Index Scan` начал бы многократно
перечитывать одни и те же страницы и хаотично прыгать по диску. Плата за это — потеря
упорядоченности, поэтому при `ORDER BY` планировщик часто предпочитает `Index Scan`
(это видно в заданиях 14 и 15).

## Задание 11. Несколько условий и несколько индексов

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID';
```
```
Bitmap Heap Scan on orders  (cost=4.51..47.62 rows=3) (actual time=0.336..0.337 rows=0)
  Recheck Cond: (user_id = 123)
  Filter: ((status)::text = 'PAID'::text)
  Rows Removed by Filter: 6
  ->  Bitmap Index Scan on idx_orders_user_id  (actual rows=6)
        Index Cond: (user_id = 123)
Execution Time: 0.382 ms
```

**1. Использует ли PostgreSQL один индекс или несколько?**
Только **один** — `idx_orders_user_id`. Индекс по `status` проигнорирован, условие по
статусу применено как обычный `Filter` уже после чтения строк из таблицы.

**2. Есть ли в плане BitmapAnd?**
В этом запросе — **нет**, и это правильное решение планировщика. `user_id = 123` уже даёт
всего 6 строк; проверить у них статус в памяти дешевле, чем читать 213 страниц индекса
`idx_orders_status` ради 250 000 адресов и пересекать два битмапа.

`BitmapAnd` появляется, когда **оба** условия среднеселективны:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id BETWEEN 100 AND 400 AND status = 'PAID';
```
```
Bitmap Heap Scan on orders  (cost=2807.62..5054.64 rows=711) (actual time=10.738..15.664 rows=722)
  Recheck Cond: ((user_id >= 100) AND (user_id <= 400) AND ((status)::text = 'PAID'::text))
  Heap Blocks: exact=699
  ->  BitmapAnd  (actual time=10.613..10.615 rows=0 loops=1)
        ->  Bitmap Index Scan on idx_orders_user_id   (actual rows=2923)
        ->  Bitmap Index Scan on idx_orders_status    (actual rows=249807)
Execution Time: 15.886 ms
```

**3. Почему PostgreSQL может объединять результаты нескольких индексов?**
Потому что битовая карта — это структура, над которой естественно выполняются логические
операции. Два `Bitmap Index Scan` строят по карте каждый, `BitmapAnd` побитово их пересекает,
и к таблице идёт только результат: 2 923 ∩ 249 807 = 722 строки, 699 страниц вместо 10 827.

Это спасательный круг, когда подходящего составного индекса нет. Но он **дорог**:
из 15.886 мс целых 10.6 мс ушло на построение карты по `idx_orders_status` — пришлось
вычитать 249 807 адресов, чтобы почти все их потом выбросить. Насколько это хуже
составного индекса — измерено в следующем задании.

## Задание 12. Составной индекс

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);  -- 20 MB
```

```
Index Scan using idx_orders_user_status on orders  (cost=0.42..16.48 rows=3) (actual time=0.029..0.029 rows=0)
  Index Cond: ((user_id = 123) AND ((status)::text = 'PAID'::text))
  Buffers: shared hit=3
Execution Time: 0.056 ms
```

### Сравнение вариантов

Запрос `WHERE user_id = 123 AND status = 'PAID'` (высокоселективное первое условие):

| Вариант | План | `Buffers` | `Execution Time` |
|---|---|---|---|
| Два отдельных индекса | Bitmap Heap Scan + `Filter` по статусу | 9 | 0.065 мс |
| **Составной `(user_id, status)`** | `Index Scan`, оба условия в `Index Cond` | **3** | **0.056 мс** |

Запрос `WHERE user_id BETWEEN 100 AND 400 AND status = 'PAID'` (оба условия среднеселективны):

| Вариант | План | `Buffers` (индексная часть) | `Execution Time` |
|---|---|---|---|
| Два отдельных индекса | `BitmapAnd` | 219 | 15.886 мс |
| **Составной `(user_id, status)`** | один `Bitmap Index Scan` | **10** | **1.383 мс** |

**в 11.5 раза быстрее, в 22 раза меньше страниц индекса.**

**1. Какой вариант оказался эффективнее?**
Составной — в обоих сценариях. На точечном запросе выигрыш скромный (0.065 → 0.056 мс),
потому что оба плана и так укладываются в доли миллисекунды. А вот на `BitmapAnd`-сценарии
разница принципиальная: 15.886 → 1.383 мс. Причина в том, что составной индекс сразу
находит нужный диапазон в дереве, тогда как `BitmapAnd` вынужден построить карту из
249 807 записей и почти всю её отбросить.

Исчез и `Rows Removed by Filter`: оба условия ушли в `Index Cond`.

**2. Всегда ли составной индекс лучше нескольких отдельных?**
Нет. Составной `(A, B)`:
- **не работает** для запросов только по `B` (правило левого префикса, задание 13);
- **больше по размеру**: 20 MB против 9088 kB + 6848 kB ≈ 15.6 MB у двух отдельных;
- **сильнее замедляет запись**, так как ключ длиннее;
- **не заменяет** отдельный индекс по `B`, если такие запросы есть.

Отдельные индексы гибче: `idx(A)` и `idx(B)` обслуживают запросы по `A`, по `B` и (через
`BitmapAnd`) по `A AND B` — пусть и медленно. Составной обслуживает `A` и `A AND B` идеально,
но по `B` бесполезен.

**3. От чего зависит выбор?**

| Условие | Решение |
|---|---|
| `A AND B` — частый, горячий запрос | составной `(A, B)` |
| `A` и `B` запрашиваются независимо | два отдельных |
| По `B` отдельно не ищут никогда | составной `(A, B)`, отдельный по `B` не нужен |
| Нужен `ORDER BY B` при `WHERE A = ?` | **только составной** `(A, B)` — иначе `Sort` |
| Много разных комбинаций, запись критична | отдельные + `BitmapAnd` как компромисс |

Правило порядка колонок для равенств (из лекции): **высокоселективные левее**.
Здесь `user_id` (91 762 значения) слева, `status` (4 значения) справа — и это верно.
Обратный порядок `(status, user_id)` заставил бы сначала спуститься в четверть таблицы.

Отдельный полезный эффект: составной `(user_id, status)` делает индекс `idx_orders_user_id`
избыточным — он является его левым префиксом. Именно этот приём применён в миграции сервиса.

## Задание 13. Порядок колонок в составном индексе

Созданы два индекса-близнеца, по 30 MB каждый:
```sql
CREATE INDEX idx_orders_user_created_at ON orders(user_id, created_at);
CREATE INDEX idx_orders_created_at_user ON orders(created_at, user_id);
```

### Результаты (индексы принудительно изолированы, чтобы сравнивать честно)

| Запрос | `(user_id, created_at)` | `(created_at, user_id)` |
|---|---|---|
| **Q1** `user_id = 123` | ✅ `Bitmap Index Scan`, 0.102 мс, 9 страниц | ❌ не применим (левый префикс — `created_at`) |
| **Q2** `user_id = 123 AND created_at > 30d` | ✅ `Index Scan`, оба условия в `Index Cond`, **0.046 мс, 3 страницы** | ⚠️ `Index Scan`, **5.730 мс, 164 страницы** |
| **Q3** `created_at > 30d` | ❌ 179.163 мс, прочитано 3 831 страница индекса | ✅ `Index Scan`, 41.794 мс |

Запрос 2 через «неправильный» индекс — **в 124 раза медленнее**, хотя формально индекс
используется и оба условия стоят в `Index Cond`:

```
Index Scan using idx_orders_created_at_user on orders (actual time=5.700..5.701 rows=0)
  Index Cond: ((created_at >= (now() - '30 days'::interval)) AND (user_id = 123))
  Buffers: shared read=164
Execution Time: 5.730 ms
```

Запрос 3, принудительно направленный в `(user_id, created_at)`:
```
Bitmap Index Scan on idx_orders_user_created_at (actual time=154.332..154.332 rows=42005)
  Index Cond: (created_at > (now() - '30 days'::interval))
  Buffers: shared read=3831 written=1527
Execution Time: 179.163 ms
```
3 831 страница — это **полный обход индекса**. `created_at` стоит вторым, дерево по нему
не отсортировано, поэтому пришлось просмотреть всё.

**1. Как порядок колонок влияет на возможность использования индекса?**
Действует **правило левого префикса**. B-tree сортирует данные слева направо: сначала по
первой колонке, внутри одинаковых значений — по второй. Индекс `(A, B)` применим для
`WHERE A = ?`, `WHERE A = ? AND B = ?`, `WHERE A = ? ORDER BY B`, но **не** для `WHERE B = ?`.

Важный нюанс, который показал эксперимент: PostgreSQL умеет использовать индекс и по
непервой колонке (Q2 через `(created_at, user_id)`, Q3 через `(user_id, created_at)`), но
это не поиск, а **полный или частичный обход индекса с проверкой условия на каждой записи**.
Формально «индекс используется», фактически это медленнее в 100+ раз. Именно поэтому нельзя
судить об оптимизации по одному лишь присутствию имени индекса в плане.

**2. Почему (user_id, created_at) и (created_at, user_id) — разные индексы?**
Это разный физический порядок записей в дереве, как два разных телефонных справочника:

```
(user_id, created_at):          (created_at, user_id):
  123 | 2026-01-05                2026-01-05 | 123
  123 | 2026-03-12                2026-01-05 | 987
  123 | 2026-09-01                2026-03-12 | 123
  124 | 2026-02-08                2026-02-08 | 124
```

Слева все заказы пользователя 123 лежат **подряд и уже отсортированы по дате** — можно
одним спуском в дерево получить и выборку, и сортировку. Справа они «размазаны» по всему
дереву: чтобы собрать заказы одного пользователя, нужно пройти весь диапазон дат.

**3. Какой индекс лучше для каждого запроса?**

| Запрос | Оптимальный индекс | Почему |
|---|---|---|
| Q1 `user_id = 123` | `(user_id, created_at)` | `user_id` — левый префикс |
| Q2 `user_id = 123 AND created_at > ?` | **`(user_id, created_at)`** | равенство слева, диапазон справа — формула из лекции |
| Q3 `created_at > ?` | `(created_at, user_id)` или одиночный `(created_at)` | `created_at` — левый префикс |

Для Q2 это прямая иллюстрация правила **(Равенства, ..., Диапазон)**: после первой
колонки с условием диапазона B-tree перестаёт эффективно фильтровать по последующим,
поэтому колонку с `>`/`<`/`BETWEEN` всегда ставим последней.

## Задание 14. WHERE + ORDER BY

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 123 ORDER BY created_at DESC;
```

**До** (доступен только одиночный `idx_orders_user_id`) — операция `Sort` присутствует:
```
Sort  (cost=47.79..47.81 rows=11) (actual time=0.226..0.228 rows=6 loops=1)
  Sort Key: created_at DESC
  Sort Method: quicksort  Memory: 25kB
  ->  Bitmap Heap Scan on orders  (actual rows=6)
        Recheck Cond: (user_id = 123)
Execution Time: 0.307 ms
```

```sql
CREATE INDEX idx_orders_user_created_at_desc ON orders(user_id, created_at DESC);  -- 30 MB
```

### Честный результат: Sort сам по себе не исчез

После создания индекса план **остался прежним** — `Sort` над `Bitmap Heap Scan`.
Это не ошибка эксперимента, а осмысленное решение планировщика: у `user_id = 123` всего
6 строк, отсортировать их в памяти (`quicksort  Memory: 25kB`) стоит дешевле, чем идти
упорядоченным `Index Scan`.

Проверим гипотезу, запретив bitmap-план:
```
SET enable_bitmapscan = off;
Index Scan using idx_orders_user_created_at_desc on orders (actual time=0.027..0.044 rows=6)
  Index Cond: (user_id = 123)
Execution Time: 0.123 ms     ← Sort отсутствует
```

Индекс полностью работоспособен — просто на шести строках он не окупается.
Чтобы увидеть реальный эффект, нужен запрос, где сортировать есть что:

| Сценарий | До индекса | После индекса | Выигрыш |
|---|---|---|---|
| `user_id BETWEEN 1 AND 5000 ORDER BY created_at DESC LIMIT 20` | `Index Scan Backward` + `Filter`, 332 страницы, **2.759 мс** | `Index Scan Backward`, 25 страниц, **0.123 мс** | **22×** |
| «Тяжёлый» пользователь (27 заказов), `LIMIT 20` | `Sort` + Bitmap, 30 страниц, **0.566 мс** | `Index Scan`, 23 страницы, **0.167 мс** | **3.4×** |

**1. Исчезла ли операция Sort?**
Для `user_id = 123` — нет, и объяснение выше. Как только строк становится достаточно
(запрос по 5000 пользователей или пользователь с 27 заказами), `Sort` из плана уходит,
и запрос ускоряется в 3–22 раза. На данных собственного сервиса, где у пользователя
20 000 бронирований, `Sort` исчезает уверенно и даёт ускорение в 26 раз (см. задание 29).

**2. Почему индекс может использоваться для сортировки?**
Потому что B-tree **уже хранит данные упорядоченными**: в листьях записи лежат
отсортированными по ключу, а листья связаны в двусвязный список. Прочитав их подряд,
СУБД получает готовую последовательность — сортировать нечего.

Это даёт три эффекта:
- узел `Sort` исчезает целиком;
- не расходуется `work_mem` (а при нехватке — `Sort Method: external merge Disk`,
  реальный пример в задании 17: 16 232 kB записано на диск);
- **`LIMIT` начинает работать по-настоящему**: `Sort` обязан получить *все* строки перед
  выдачей первой, а упорядоченный `Index Scan` останавливается ровно на 20-й строке.

Двусвязность листьев позволяет читать индекс и в обратную сторону — отсюда
`Index Scan Backward`. Поэтому для одноколоночной сортировки `DESC` в объявлении индекса
необязателен.

**3. Почему порядок колонок важен в данном случае?**
Индекс `(user_id, created_at DESC)` даёт «в подарок» сортировку только **внутри** группы
с одинаковым `user_id`. При `WHERE user_id = 123` мы попадаем ровно в одну такую группу —
и она уже упорядочена по дате. Индекс `(created_at DESC, user_id)` этого не даёт: строки
нужного пользователя разбросаны по всему дереву, и после их сбора всё равно потребуется `Sort`.

Направление `DESC` в ключе имеет значение при сортировке **по нескольким колонкам с разным
направлением** (`ORDER BY a ASC, b DESC`) — вот там обратный проход не спасёт.

## Задание 15. Pagination Query (реальный API-запрос)

Эндпоинт `GET /users/{user_id}/orders`:
```sql
SELECT * FROM orders WHERE user_id = 123 ORDER BY created_at DESC LIMIT 20;
```

**1. План до оптимизации** (доступен только `idx_orders_user_id`):
```
Limit  (cost=47.79..47.81 rows=11) (actual time=0.075..0.077 rows=6)
  ->  Sort  (cost=47.79..47.81 rows=11)
        Sort Key: created_at DESC
        Sort Method: quicksort  Memory: 25kB
        ->  Bitmap Heap Scan on orders
              Recheck Cond: (user_id = 123)
Execution Time: 0.140 ms
```

**2–3. Подобранный индекс и повторный замер:**
```sql
CREATE INDEX idx_orders_user_created_at_desc ON orders(user_id, created_at DESC);
```
```
Limit  (cost=0.42..48.62 rows=11) (actual time=0.029..0.047 rows=6)
  ->  Index Scan using idx_orders_user_created_at_desc on orders
        Index Cond: (user_id = 123)
Execution Time: 0.123 ms      ← Sort отсутствует
```

**4–5. Сравнение планов и времени**

| Метрика | До | После |
|---|---|---|
| Тип Scan | `Bitmap Heap Scan` + `Sort` | `Index Scan` |
| Операция `Sort` | есть (`quicksort  Memory: 25kB`) | **отсутствует** |
| Сколько строк нужно прочитать до выдачи первой | все строки пользователя | **ровно 1** |
| `Execution Time` | 0.140 мс | 0.123 мс |

На пользователе с 27 заказами: 0.566 мс → 0.167 мс (**3.4×**).
На данных сервиса с 20 014 бронирований: 2.863 мс → 0.110 мс (**26×**, задание 29).

**6. Объяснение выбранной структуры индекса**

```
CREATE INDEX idx_orders_user_created_at_desc ON orders(user_id, created_at DESC);
                                                       ↑        ↑
                                          равенство (WHERE)  сортировка (ORDER BY)
```

- `user_id` **первым**, потому что это условие `WHERE` на равенство и колонка
  высокоселективна (91 762 различных значения). Спуск по дереву сразу отсекает всё лишнее.
- `created_at` **вторым**, потому что внутри группы одного пользователя записи оказываются
  уже отсортированными по дате — узел `Sort` становится не нужен.
- `DESC` **в ключе**, чтобы порядок индекса совпадал с `ORDER BY created_at DESC` буквально.
  Строго говоря, PostgreSQL справился бы и с `ASC` через `Index Scan Backward`, но явное
  `DESC` делает намерение читаемым и понадобится, если в сортировку добавят вторую колонку.

Это тот самый случай, когда **один индекс закрывает и фильтрацию, и сортировку, и `LIMIT`**.
Ключевое свойство — стоимость перестаёт зависеть от числа заказов пользователя: сколько бы
их ни было, читаются ровно первые 20.

## Задание 16. Index Only Scan

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT id, user_id FROM orders WHERE user_id = 123;
```
```
Bitmap Heap Scan on orders  (actual time=0.026..0.041 rows=6 loops=1)
  Recheck Cond: (user_id = 123)
  Heap Blocks: exact=6
  Buffers: shared hit=9
Execution Time: 0.068 ms
```

`Index Only Scan` **не получен**: в индексе `(user_id)` нет колонки `id`, за ней приходится
идти в таблицу. Убираем `id` из выборки:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT user_id FROM orders WHERE user_id = 123;
```
```
Index Only Scan using idx_orders_user_created_at_desc on orders  (actual time=0.027..0.030 rows=6)
  Index Cond: (user_id = 123)
  Heap Fetches: 0
  Buffers: shared hit=4
Execution Time: 0.060 ms
```

`Heap Fetches: 0` — к таблице не было **ни одного** обращения, 4 страницы вместо 9.

**1. Чем Index Only Scan отличается от обычного Index Scan?**

| | `Index Scan` | `Index Only Scan` |
|---|---|---|
| Шаги | индекс → **таблица по TID** | только индекс |
| Обращений к heap | по одному на строку | **0** (`Heap Fetches: 0`) |
| Условие применимости | нужные колонки могут быть где угодно | **все** колонки из `SELECT`, `WHERE`, `ORDER BY`, `GROUP BY` есть в индексе |
| `Buffers` в примере | 9 | 4 |

**2. Почему PostgreSQL может не обращаться к основной таблице?**
Потому что в листьях B-tree рядом с ключом лежит и само значение. Если запросу нужны
только проиндексированные колонки, ответ формируется прямо из индекса.

Но есть тонкость, специфичная для PostgreSQL: **индекс не хранит информацию о видимости
версий строк** (MVCC). Строка может быть удалена или обновлена другой транзакцией, а
запись в индексе ещё остаётся. Поэтому используется **карта видимости** (visibility map) —
компактная битовая структура, отмечающая страницы, все версии строк в которых видимы всем
транзакциям. Если страница отмечена — heap не читается; если нет — приходится идти
в таблицу, и это отражается в счётчике `Heap Fetches`.

В нашей базе карта полная, что и позволило получить `Heap Fetches: 0`:
```
relname | relpages | reltuples | relallvisible
orders  |    10827 |   1000000 |         10827      ← relallvisible = relpages
```

**3. Какие условия необходимы для Index Only Scan?**
1. **Все** колонки запроса (`SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`, `JOIN`) входят в
   индекс — как ключ или как `INCLUDE`.
2. Страницы отмечены в карте видимости, то есть по таблице недавно проходил
   `VACUUM` / автовакуум. Сразу после массовой записи `Index Only Scan` деградирует
   в обычный `Index Scan` с ненулевым `Heap Fetches`.
3. Тип индекса поддерживает возврат значений (B-tree — да; GIN, например, нет).
4. Планировщик счёл такой план дешевле остальных.

### Дополнительное задание: покрывающий индекс INCLUDE

```sql
CREATE INDEX idx_orders_user_id_include ON orders(user_id) INCLUDE (id, status, created_at);
VACUUM ANALYZE orders;
```

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT id, status, created_at FROM orders WHERE user_id = 123;
```
```
Index Only Scan using idx_orders_user_id_include on orders  (actual time=0.033..0.037 rows=6)
  Index Cond: (user_id = 123)
  Heap Fetches: 0
  Buffers: shared hit=4
Execution Time: 0.091 ms
```

Контрпример — добавляем `amount`, которого в индексе нет:
```
Bitmap Heap Scan on orders  (actual rows=6)      ← Index Only Scan потерян
  Buffers: shared hit=9
```

| Индекс | Размер |
|---|---|
| `idx_orders_user_id (user_id)` | 9088 kB |
| `idx_orders_user_id_include (user_id) INCLUDE (id, status, created_at)` | **52 MB** |

Отличие `INCLUDE` от составного индекса: колонки в `INCLUDE` хранятся **только в листьях**
и не участвуют ни в сортировке, ни в поиске. Плюсы — дерево не раздувается лишними
уровнями, а на `UNIQUE`-индексе уникальность по-прежнему проверяется только по ключу.
Минус хорошо виден по цифрам: индекс вырос почти в 6 раз, то есть покрытие — не бесплатный
приём, а размен «место и стоимость записи» на «отсутствие обращений к таблице».

## Задание 17. Partial Index

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'NEW' ORDER BY created_at;
```

**До** (доступен обычный `idx_orders_status`):
```
Sort  (cost=47284.90..47903.07 rows=247267) (actual time=297.970..351.704 rows=250663)
  Sort Key: created_at
  Sort Method: external merge  Disk: 16232kB       ← сортировка не влезла в work_mem
  Buffers: shared hit=11043 read=1, temp read=2029 written=2035
  ->  Bitmap Heap Scan on orders  (actual rows=250663)
        Heap Blocks: exact=10827                    ← прочитана вся таблица
Execution Time: 369.329 ms
```

```sql
CREATE INDEX idx_orders_new ON orders(created_at) WHERE status = 'NEW';   -- 5520 kB
```

**После**, полная выборка: 260.815 мс — план не изменился (`Bitmap` + `external merge`).
Планировщик прав: запрос требует все 250 663 строки, читать их через индекс смысла нет.

**А вот с `LIMIT` — типичным для API — картина другая:**

| Вариант | План | `Buffers` | `Execution Time` |
|---|---|---|---|
| Без частичного индекса, `LIMIT 100` | `Index Scan` по `idx_orders_created_at` + `Filter`, `Rows Removed by Filter: 275` | 379 | 0.902 мс |
| **С частичным индексом, `LIMIT 100`** | `Index Scan using idx_orders_new`, **фильтра нет** | **103** | **0.332 мс** |

**в 2.7 раза быстрее и в 3.7 раза меньше чтений.**

### Настоящая сила partial index — на редком подмножестве

Условие `status = 'NEW'` покрывает 25% таблицы, что для частичного индекса многовато.
Возьмём действительно редкое подмножество — `status = 'NEW' AND amount < 100`
(**2 463 строки, 0.246%**):

| | План | `Buffers` | `Execution Time` |
|---|---|---|---|
| До | `BitmapAnd` (`idx_orders_amount` × `idx_orders_status`) | 2 450 | 16.053 мс |
| **После** `CREATE INDEX ... ON orders(created_at) WHERE status='NEW' AND amount < 100` | один `Bitmap Index Scan` | 2 214 | **4.268 мс** |

**в 3.8 раза быстрее**, а размер индекса — **72 kB** против 21 MB у полного по `created_at`,
то есть **в 298 раз меньше**.

**1. В чём преимущество partial index?**
- **Размер.** 5520 kB против 21 MB (в 3.8 раза) в первом случае и 72 kB против 21 MB
  (в 298 раз) во втором. Маленький индекс лучше кэшируется, а дерево получается ниже.
- **Скорость записи.** Индекс обновляется **только** для строк, попадающих под условие.
  Вставка заказа со статусом `PAID` вообще не трогает `idx_orders_new` — экономия на
  75% операций записи.
- **Точность плана.** Условие индекса становится частью его определения, поэтому в плане
  исчезает `Filter` (сравните: `Rows Removed by Filter: 275` было — стало пусто).
- **Статистика.** PostgreSQL хранит для частичного индекса отдельную оценку строк,
  и планировщик точнее предсказывает кардинальность.

**2. В каких случаях partial index будет полезен?**
- **Сильный перекос значений**: 95% `published` и 5% `draft` — индексировать имеет смысл
  только `draft`.
- **«Горячие» рабочие очереди**: `WHERE status IN ('pending','processing')` — незакрытые
  задачи, которых всегда мало, тогда как исторических записей миллионы.
- **Мягкое удаление**: `WHERE deleted_at IS NULL`.
- **Условная уникальность**: `CREATE UNIQUE INDEX ... ON users(email) WHERE deleted_at IS NULL`
  — уникальность только среди активных пользователей; обычным `UNIQUE` этого не выразить.
- **Отсечение `NULL`** в колонке, где их подавляющее большинство.

**3. Почему нельзя использовать один partial index для всех типов запросов?**
Потому что планировщик обязан **доказать**, что условие запроса логически влечёт условие
индекса. Если этого доказательства нет, индекс не может быть использован — иначе результат
был бы неполным. Проверено экспериментом:

```sql
SELECT * FROM orders WHERE status = 'PAID' ORDER BY created_at LIMIT 100;
```
```
Index Scan using idx_orders_created_at on orders     ← idx_orders_new игнорируется
  Filter: ((status)::text = 'PAID'::text)
Execution Time: 0.784 ms
```

`idx_orders_new` содержит только строки со `status = 'NEW'`, поэтому для `status = 'PAID'`
он не просто неэффективен — он **непригоден в принципе**. Отсюда практический вывод:
частичный индекс — узкоспециализированный инструмент под конкретный шаблон запроса.
Заводить по частичному индексу на каждое значение `status` — значит вернуться к тем же
затратам на запись, только в худшем виде.

## Задание 18. Expression Index

Создана таблица `users` (500 001 строка) и обычный индекс по `email`.

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM users WHERE LOWER(email) = 'test@example.com';
```
```
Gather  (cost=1000.00..10057.01 rows=2500) (actual time=196.496..204.216 rows=1 loops=1)
  Workers Planned: 2
  ->  Parallel Seq Scan on users  (actual rows=0 loops=3)
        Filter: (lower((email)::text) = 'test@example.com'::text)
        Rows Removed by Filter: 166667
        Buffers: shared hit=5682
Execution Time: 204.244 ms
```

**Индекс `idx_users_email` полностью проигнорирован.** Для контраста — тот же поиск без функции:
```sql
SELECT * FROM users WHERE email = 'Test@Example.com';
```
```
Index Scan using idx_users_email on users  (actual time=0.060..0.062 rows=1)
Execution Time: 0.079 ms
```

### Почему обычный индекс по email не используется?

Индекс `idx_users_email` хранит значения **в исходном виде**: `'Test@Example.com'`,
`'User42_ab3f@Example.COM'`, отсортированные по правилам сравнения строк. Запрос же ищет
не `email`, а **результат функции** `LOWER(email)` — совершенно другую величину.

СУБД не может «на лету» применить функцию к отсортированному дереву: порядок значений
после `LOWER()` в общем случае иной, и левый префикс перестаёт работать. Формально:
индекс построен по выражению `email`, а условие — по выражению `LOWER(email)`; они не
совпадают синтаксически, поэтому индекс неприменим. Приходится читать все 500 001 строк
и вычислять `LOWER()` для каждой.

Ровно та же ловушка возникает при `WHERE DATE(created_at) = '2026-09-09'`,
`WHERE user_id::text = '123'` и `WHERE email LIKE '%@example.com'` (ведущий `%`).

```sql
CREATE INDEX idx_users_lower_email ON users(LOWER(email));
```
```
Index Scan using idx_users_lower_email on users  (actual time=0.021..0.023 rows=1 loops=1)
  Index Cond: (lower((email)::text) = 'test@example.com'::text)
  Buffers: shared hit=4
Execution Time: 0.039 ms
```

| Метрика | Обычный индекс | Индекс по выражению |
|---|---|---|
| Тип Scan | `Parallel Seq Scan` | `Index Scan` |
| `Execution Time` | 204.244 мс | **0.039 мс** |
| `Buffers` | 5 682 | **4** |
| Размер индекса | 37 MB | 37 MB |

**Ускорение в 5237 раз** при том же размере индекса.

### Вывод: почему выражение в запросе влияет на использование индекса

Индекс — это отсортированное хранилище **конкретного выражения**, а не колонки как таковой.
Планировщик может применить индекс, только если выражение в `WHERE` **совпадает** с
выражением, по которому индекс построен. Любая функция или приведение типа поверх колонки
делает старый индекс непригодным.

Два способа решения:
1. **Убрать функцию из запроса** — если это возможно (например, хранить email уже в нижнем
   регистре или использовать тип `citext`).
2. **Построить индекс по тому же выражению** — `CREATE INDEX ON users(LOWER(email))`.
   Тогда PostgreSQL заранее вычисляет `LOWER(email)` для каждой строки и хранит результат
   отсортированным.

Плата: выражение вычисляется при **каждой** вставке и обновлении строки, а функция обязана
быть `IMMUTABLE` (для одного входа всегда один и тот же результат). Поэтому,
например, `CREATE INDEX ON orders(age(created_at))` создать нельзя — результат зависит
от текущего времени.

## Задание 19. Цена индексов (влияние на запись)

Две одинаковые таблицы, отличаются только числом индексов. В каждую вставлено по 300 000 строк.

| Операция | Без доп. индексов (только PK) | С 6 индексами | Замедление |
|---|---|---|---|
| `INSERT` 300 000 строк | **2 315 мс** | **10 529 мс** | **в 4.55 раза** |
| `UPDATE` 50 000 строк, колонка **не в индексах** | 563 мс | 2 284 мс | в 4.06 раза |
| `UPDATE` 50 000 строк, колонка **в индексах** | 511 мс | 2 008 мс | в 3.93 раза |
| `DELETE` 50 000 строк | 184 мс | **35 мс** | замедления нет |

Размеры после всех операций:

| Таблица | Данные | Индексы | Индексы, % от данных |
|---|---|---|---|
| `orders_no_idx` (только PK) | 34 MB | 8808 kB | 25.6% |
| `orders_with_idx` (7 индексов) | 34 MB | 66 MB | **194.9%** |
| `orders` (8 индексов, 1 млн строк) | 85 MB | **247 MB** | **291.9%** |

На таблице `orders` **индексы занимают почти втрое больше места, чем сами данные.**

**1. Как изменилось время выполнения INSERT?**
Выросло с 2 315 мс до 10 529 мс — **в 4.55 раза**. Шесть дополнительных индексов
превратили одну операцию записи в семь. В пересчёте: 7.7 мкс на строку против 35.1 мкс.

**2. Почему?**
Вставка одной строки при наличии индексов — это не одна, а `1 + N` операций:
1. Запись версии строки в heap (в первую подходящую страницу).
2. Для **каждого** индекса: спуск по B-tree до нужного листа, вставка пары
   «ключ → TID» с сохранением порядка сортировки.
3. При переполнении листа — **split страницы**: создание новой, перераспределение записей,
   обновление ссылок в родительском узле; изредка это каскадно увеличивает высоту дерева.
4. Все изменения — и heap, и каждого индекса — записываются в WAL, что увеличивает объём
   журнала и нагрузку на диск.

Дополнительно: heap-вставка последовательна (данные пишутся в конец), а вот вставки в
индексы попадают в **случайные** места дерева — по алфавиту для строк, по порядку для чисел.
Отсюда нелинейный рост стоимости.

Показателен результат `UPDATE`: колонка `product_id` не входит **ни в один** индекс,
но замедление всё равно 4.06×. Причина в MVCC: `UPDATE` в PostgreSQL — это «пометить
старую версию мёртвой + вставить новую». Новая версия строки получает **новый TID**,
и если она не помещается на ту же страницу, обновить приходится **все** индексы, даже
те, чьи колонки не менялись. Механизм HOT-обновлений (Heap-Only Tuple) спасает от этого
только когда на странице есть свободное место и ни одна индексируемая колонка не затронута —
здесь свободного места на плотно набитых страницах не оказалось.

**3. Что происходит с индексами при добавлении новой строки?**
Для каждого индекса выполняется вставка записи `(значение_ключа, TID)` в лист B-tree
с сохранением сортировки, при необходимости — со split-ом страницы, и всё это журналируется
в WAL. Соответственно, `N` индексов означают `N`-кратную работу на каждой вставке.

**Отдельно про DELETE.** Замедления не обнаружено (184 мс против 35 мс — таблица с
индексами оказалась даже быстрее, что объясняется прогретым кэшем во втором прогоне).
Это не аномалия, а следствие MVCC: `DELETE` **не удаляет** записи из индексов, а лишь
помечает версию строки мёртвой (`xmax`). Реальная чистка индексов происходит позже,
в фоне, силами `VACUUM` / автовакуума. То есть стоимость удаления не исчезает — она
**откладывается** и переносится на фоновый процесс, а до его прихода индексы продолжают
занимать место и содержать ссылки на мёртвые строки.

**3. Можно ли автоматически считать индекс с idx_scan = 0 бесполезным?**
**Нет.** `idx_scan = 0` — повод разобраться, а не команда к удалению. Причины нулевого
счётчика могут быть законными:

- **Статистика была сброшена** (`pg_stat_reset()`) или сервер перезапущен —
  проверять надо `stats_reset` в `pg_stat_database`.
- **Индекс молодой** — создан вчера и ещё не попал ни в один запрос.
- **Редкая, но критичная нагрузка**: месячный отчёт, квартальная выгрузка, аварийный
  ручной запрос администратора. Ноль за неделю ничего не доказывает.
- **Индекс обеспечивает ограничение целостности.** `UNIQUE` и `PRIMARY KEY` реализованы
  через индекс: `idx_scan` может быть нулевым, но при удалении пропадёт **гарантия
  уникальности**. Такие индексы удалять нельзя.
- **Индекс поддерживает внешний ключ.** Без него `DELETE` или `UPDATE` в родительской
  таблице приводит к полному сканированию дочерней при проверке `FK`. Эти проверки
  не всегда попадают в `idx_scan`.
- **Реплики.** На physical standby своя статистика: индекс, бесполезный на мастере, может
  активно работать на читающей реплике.

**4. Какие риски существуют при удалении индекса?**
- **Деградация запросов**, которые опирались на него, — вплоть до `Seq Scan` по таблице
  на миллионы строк. Проявляется мгновенно и под нагрузкой.
- **Потеря ограничения целостности** при удалении `UNIQUE`-индекса — в базу немедленно
  начинают попадать дубликаты, и откат уже не восстановит данные.
- **Долгое восстановление.** Обратное создание индекса на большой таблице занимает минуты
  или часы и берёт блокировку `SHARE`, блокирующую запись (снимается только через
  `CREATE INDEX CONCURRENTLY`, который в 2–3 раза медленнее и не работает внутри транзакции).
- **Каскадный эффект на планы.** Исчезновение индекса меняет оценки стоимости и может
  перестроить планы соседних запросов, включая порядок соединений в сложных `JOIN`.
- **Замедление проверок FK**, если индекс поддерживал внешний ключ.

Безопасный порядок действий:
1. Убедиться, что индекс не `UNIQUE`, не `PRIMARY KEY` и не поддерживает FK.
2. Собирать `pg_stat_user_indexes` **не менее одного полного бизнес-цикла** (месяц, квартал).
3. Проверить все реплики.
4. Сначала **пометить** индекс невидимым для планировщика — в PostgreSQL это
   `UPDATE pg_index SET indisvalid = false` в транзакции, либо в тестовой среде
   `SET enable_indexscan = off`; понаблюдать за планами.
5. Удалять через `DROP INDEX CONCURRENTLY`, имея наготове готовый скрипт обратного создания.

## Задание 21. Финальная оптимизация запроса

```sql
SELECT id, amount, status, created_at
FROM orders
WHERE user_id = $1 AND status = 'PAID' AND created_at >= NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 50;
```

### 1–2. EXPLAIN ANALYZE и анализ текущего плана

Чистый замер «до» (составные индексы временно скрыты, доступны только одиночные):
```
Limit  (cost=47.71..47.72 rows=1 width=29) (actual time=0.346..0.348 rows=0 loops=1)
  Buffers: shared hit=4 read=8
  ->  Sort  (cost=47.71..47.72 rows=1 width=29)
        Sort Key: created_at DESC
        Sort Method: quicksort  Memory: 25kB
        ->  Bitmap Heap Scan on orders  (actual rows=0 loops=1)
              Recheck Cond: (user_id = 123)
              Filter: (((status)::text = 'PAID'::text) AND (created_at >= (now() - '30 days'::interval)))
              Rows Removed by Filter: 6
              Heap Blocks: exact=6
              ->  Bitmap Index Scan on idx_orders_user_id
                    Index Cond: (user_id = 123)
Execution Time: 0.437 ms
```

### 3. Потенциальные проблемы

1. **Из трёх условий индексом обслуживается только одно.** `user_id` попал в `Index Cond`,
   а `status` и `created_at` остались в `Filter` — то есть применяются к строкам уже
   **после** их чтения из таблицы. `Rows Removed by Filter: 6` — все прочитанные строки
   оказались выброшены впустую.
2. **Присутствует `Sort`.** Сортировка выполняется в памяти после сбора всех строк,
   а значит `LIMIT 50` не может остановить чтение досрочно: чтобы отдать 50 строк,
   узел `Sort` обязан сначала получить их все.
3. **Обращение к heap ради выброшенных строк.** `Heap Blocks: exact=6` — страницы таблицы
   прочитаны только чтобы проверить `status` и `created_at`.
4. **Проблема масштабируется линейно.** У пользователя с 20 000 бронирований будут
   прочитаны, а затем отсортированы все 20 000 строк — ради 50 нужных.

### 4–5. Предлагаемый индекс и обоснование порядка колонок

```sql
CREATE INDEX idx_orders_user_status_created_at ON orders(user_id, status, created_at DESC);
```

```
WHERE user_id = $1          -- равенство, высокая селективность (91 762 значения)  → 1-я
  AND status = 'PAID'       -- равенство, низкая селективность (4 значения)        → 2-я
  AND created_at >= ...     -- ДИАПАЗОН                                            → 3-я
ORDER BY created_at DESC    -- сортировка по той же колонке                        → DESC
```

Обоснование опирается на два правила из лекции:

- **«Равенства слева, диапазон справа».** B-tree перестаёт эффективно фильтровать по
  колонкам, стоящим **после** первого условия диапазона. Поэтому `created_at` обязан быть
  последним — иначе `user_id` и `status` не смогут сузить поиск.
- **«Высокоселективные равенства левее».** `user_id` (91 762 различных значения) отсекает
  99.999% таблицы за один спуск в дерево; `status` (4 значения) отсекает лишь 75%.
  Поставить `status` первым означало бы сначала спуститься в четверть таблицы.
- **`created_at DESC`** совпадает с `ORDER BY created_at DESC`, поэтому `Sort` не нужен,
  а `LIMIT 50` останавливает чтение ровно на 50-й записи.

Итоговая формула: **(равенство по самой селективной, равенство по менее селективной,
диапазон/сортировка)**.

### Системная находка

В моделях SQLAlchemy на колонках с `primary_key=True` дополнительно стоит `index=True`:

```python
id = Column(Integer, primary_key=True, index=True)   # было
```

`primary_key=True` **уже создаёт** уникальный индекс `<table>_pkey`. Директива `index=True`
добавляет **второй, полностью идентичный** индекс `ix_<table>_id`. В результате по всей
базе продублированы **пять** первичных ключей, из них самый дорогой — `ix_bookings_id`
на 21 MB. Планировщик выбирает какой-то один, второй лежит мёртвым грузом, но при этом
исправно обновляется при **каждой** вставке.

Это ровно та ситуация, ради которой в задании 20 разбиралось, почему `idx_scan = 0` требует
разбирательства: у `bookings_pkey` тоже ноль сканов, но удалять надо **не его**, а дубликат.

## Задание 26. Поиск потенциальных проблем

### Query 1 — `GET /api/users/{user_id}/stats`

1. **Есть ли проблема с производительностью?** Сейчас нет (0.115 мс), но есть скрытый риск
   масштабирования: `Heap Blocks: exact=40` — читается по странице на бронирование.
   У пользователя с 20 000 броней это 20 000 страниц.
2. **Используется ли Seq Scan?** Нет.
3. **Насколько селективен запрос?** Очень: `u.id = 5706` → 1 строка из 50 000;
   `b.user_id = 5706` → 40 из 1 000 000 (0.004%).
4. **Есть ли подходящий индекс?** Частично. `ix_bookings_user_id` обслуживает соединение,
   но `b.status != 'cancelled'` остаётся в `Filter` (`Rows Removed by Filter: 10`).
5. **Можно ли улучшить существующий индекс?** Да. Составной `(user_id, created_at DESC)`
   покрывает то же и заодно обслуживает Query 3 — один индекс вместо двух.
   Радикальный вариант — покрывающий `(user_id) INCLUDE (total_price, status)` дал бы
   `Index Only Scan` без обращения к таблице, но при 40 строках не окупается.
6. **Можно ли изменить SQL?** Условие `status != 'cancelled'` — неравенство,
   индексом не поддерживается в принципе. Его можно переписать как
   `status IN ('pending','confirmed','completed')` (тогда возможен `Index Cond`) или
   вынести подсчёт в денормализованные счётчики в `users`, если эндпоинт станет горячим.

### Query 2 — `GET /api/bookings?status=&from_date=`

1. **Есть ли проблема с производительностью?** **Да, серьёзная.** `COUNT(*)` для пагинации
   выполняется **63.7 мс** и читает **9 244 страницы** — всю таблицу. При этом сама
   выборка данных занимает 0.638 мс. То есть **99% времени эндпоинта тратится на подсчёт
   общего числа записей**, а не на выдачу результата.
2. **Используется ли Seq Scan?** **Да** — `Parallel Seq Scan` в Query 2b.
   Индекс `ix_bookings_status` существует, но планировщик его отверг.
3. **Насколько селективен запрос?** Средне: 165 620 строк = **16.56%** таблицы. Это как
   раз «мёртвая зона», где одиночный индекс по `status` (60% строк) бесполезен,
   а по `created_at` — недостаточно точен.
4. **Есть ли подходящий индекс?** Нет. Есть два одиночных, каждый из которых покрывает
   лишь половину условия. `BitmapAnd` планировщик тоже не выбрал — построение карты
   по 600 000 записей `confirmed` дороже честного сканирования.
5. **Можно ли улучшить?** Да — составной `(status, created_at DESC)`: равенство слева,
   диапазон справа. Дополнительный бонус: `COUNT(*)` не требует данных из таблицы,
   поэтому возможен `Index Only Scan`.
6. **Можно ли изменить SQL?** Да, и это стоит сделать отдельно от индексов:
   - `COUNT(*)` на каждой странице — антипаттерн. Варианты: считать только на первой
     странице, использовать приблизительную оценку из `pg_class.reltuples`, либо перейти
     на keyset-пагинацию (`WHERE created_at < :last_seen`), которая вообще не нуждается
     в общем счётчике.
   - Обёртка `SELECT count(*) FROM (SELECT все колонки ...)` порождена SQLAlchemy
     (`query.count()`); `count()` по одному полю читал бы меньше данных.
   - `WHERE 1=1` в конкатенации условий безвреден (планировщик его выбрасывает),
     но затрудняет чтение логов.

### Query 3 — `GET /api/users/{user_id}/bookings`

1. **Есть ли проблема с производительностью?** Да, структурная. В плане присутствует
   **`Sort`**, а значит `LIMIT 20` не работает как ограничитель: сортировка обязана
   получить **все** брони пользователя, прежде чем отдать первые 20.
2. **Используется ли Seq Scan?** Нет, но `Bitmap Heap Scan` читает все 40 строк (40 страниц),
   хотя нужны только 20.
3. **Насколько селективен запрос?** Высоко: 40 строк из 1 000 000 (0.004%).
4. **Есть ли подходящий индекс?** Только частично: `ix_bookings_user_id` закрывает `WHERE`,
   но не `ORDER BY`.
5. **Можно ли улучшить существующий индекс?** Да — это **главный кандидат** на оптимизацию.
   Составной `(user_id, created_at DESC)` закрывает и фильтр, и сортировку, и `LIMIT`.
6. **Можно ли изменить SQL?** `OFFSET` в глубокой пагинации деградирует линейно
   (`page=100` заставит прочитать и отбросить 2 000 строк) — правильное решение
   keyset-пагинация. Но для этого эндпоинта индекс важнее: OFFSET упирается в те же
   40 строк на пользователя.

## Задание 28. Реализация изменения через миграцию

Файл [`migrations/versions/002_booking_indexes.py`](../migrations/versions/002_booking_indexes.py):

```python
def upgrade() -> None:
    op.execute("CREATE INDEX ix_bookings_user_id_created_at ON bookings (user_id, created_at DESC)")
    op.execute("CREATE INDEX ix_bookings_status_created_at  ON bookings (status,  created_at DESC)")
    op.drop_index("ix_bookings_id",      table_name="bookings")   # дубликат bookings_pkey
    op.drop_index("ix_bookings_user_id", table_name="bookings")   # левый префикс нового индекса
    op.drop_index("ix_bookings_status",  table_name="bookings")   # левый префикс нового индекса

def downgrade() -> None:
    op.create_index("ix_bookings_status",  "bookings", ["status"])
    op.create_index("ix_bookings_user_id", "bookings", ["user_id"])
    op.create_index("ix_bookings_id",      "bookings", ["id"])
    op.drop_index("ix_bookings_status_created_at",  table_name="bookings")
    op.drop_index("ix_bookings_user_id_created_at", table_name="bookings")
```

### Обоснование каждого изменения

| Действие | Индекс | Почему |
|---|---|---|
| **+** | `ix_bookings_user_id_created_at (user_id, created_at DESC)` | Query 3: равенство по `user_id` слева, сортировка по `created_at` справа → убирает `Sort` и включает `LIMIT` |
| **+** | `ix_bookings_status_created_at (status, created_at DESC)` | Query 2: равенство по `status` слева, диапазон по `created_at` справа → убирает `Parallel Seq Scan` |
| **−** | `ix_bookings_id` | **полный дубликат** `bookings_pkey`: та же колонка, тот же btree. 21 MB и лишняя работа на каждой вставке при нулевой пользе |
| **−** | `ix_bookings_user_id` | стал **левым префиксом** `ix_bookings_user_id_created_at` — все запросы по `user_id` обслуживает новый индекс |
| **−** | `ix_bookings_status` | стал **левым префиксом** `ix_bookings_status_created_at`; вдобавок был вырожденным из-за селективности 60% |

Сохранены `ix_bookings_created_at` (фильтры по дате без статуса) и `ix_bookings_event_id`
(поддержка внешнего ключа и `get_event_bookings`).

Модель приведена в соответствие со схемой — [`app/models/booking.py`](../app/models/booking.py):

```python

user_id = Column(Integer, ForeignKey("users.id"), nullable=False)   # покрыт составным

```

### Воспроизводимость

Требование «изменение не должно существовать только в локальной базе» выполнено:

- миграция лежит в репозитории и применяется автоматически — в `docker-compose.yml`
  команда backend начинается с `alembic upgrade head`;
- есть рабочий `downgrade()` для отката;
- модели SQLAlchemy синхронизированы со схемой, поэтому `alembic revision --autogenerate`
  не будет пытаться пересоздать удалённые индексы.

Проверка на чистом запуске:
```
INFO  [alembic.runtime.migration] Running upgrade 001 -> 002, lab-01: индексы для bookings (scaling entity)
```
```sql
SELECT version_num FROM alembic_version;   -- 002
```

**Замечание для боевой среды.** Индексы создаются обычным `CREATE INDEX`, который берёт
блокировку `SHARE` и на время построения блокирует запись в таблицу (здесь — единицы секунд
на миллионе строк). Alembic выполняет миграции внутри транзакции, а `CREATE INDEX CONCURRENTLY`
в транзакции работать не может. Для продакшена с ненулевым трафиком этот шаг нужно выносить
отдельно — с `CONCURRENTLY` и вне транзакционного блока.

## Задание 30. Почему нельзя индексировать всё?

Ответ опирается на измерения, выполненные в этой работе.

### Размер индексов

На таблице `orders` (1 000 000 строк) с восемью индексами:

| | Размер |
|---|---|
| Данные (heap) | **85 MB** |
| Индексы | **247 MB** |
| Отношение | **291.9%** |

**Индексы заняли почти втрое больше места, чем сами данные.** На вспомогательной
`orders_with_idx` с шестью индексами — 194.9%. Один покрывающий индекс с `INCLUDE`
раздулся с 9088 kB до 52 MB (в 5.9 раза).

Причина: индекс хранит **копию** значений колонки плюс TID плюс служебные заголовки
страниц. Индекс по «широкой» колонке может оказаться сопоставим по объёму с самой таблицей.

### Стоимость хранения

Место — не только диск. Индексы конкурируют с данными за `shared_buffers`
(здесь всего 128 MB). 247 MB индексов физически не помещаются в кэш, а значит,
**лишние индексы вытесняют из памяти те страницы, которые действительно нужны**, — и
вместо ускорения дают дополнительные чтения с диска. Кроме того, индексы увеличивают
объём резервных копий, время восстановления и время построения реплики.

### INSERT

Измерено напрямую (задание 19), 300 000 строк:

| | Время |
|---|---|
| Без дополнительных индексов | **2 315 мс** |
| С 6 индексами | **10 529 мс** |
| **Замедление** | **в 4.55 раза** |

Каждая вставка превращается в `1 + N` операций: запись в heap плюс спуск по каждому
B-tree, вставка с сохранением порядка и, при переполнении листа, split страницы.
Вставки в heap последовательны, а в индексы — в случайные места дерева.

### UPDATE

| Сценарий | Без индексов | С 6 индексами | Замедление |
|---|---|---|---|
| Колонка **не входит** ни в один индекс | 563 мс | 2 284 мс | **в 4.06 раза** |
| Колонка **входит** в индексы | 511 мс | 2 008 мс | в 3.93 раза |

Самое неочевидное здесь — **первая строка**. Обновление колонки, которой нет ни в одном
индексе, всё равно замедлилось вчетверо. Причина в MVCC: `UPDATE` создаёт **новую версию
строки** с новым TID, и если она не поместилась на ту же страницу, обновить приходится
**все** индексы, включая те, чьи колонки не менялись. Оптимизация HOT спасает только
при наличии свободного места на странице.

Отсюда важный вывод: **нельзя рассуждать «этот индекс не мешает, потому что мы эту
колонку не обновляем»** — мешает.

### DELETE

| | Время |
|---|---|
| Без индексов | 184 мс |
| С 6 индексами | 35 мс |

Прямого замедления не обнаружено — и это не ошибка измерения. `DELETE` в PostgreSQL
**не трогает индексы**: он лишь помечает версию строки мёртвой, проставляя `xmax`.

Но стоимость не исчезает, а **откладывается**. Записи в индексах продолжают указывать
на мёртвые строки, пока до них не дойдёт `VACUUM`, которому придётся пройти по **каждому**
индексу таблицы. Чем больше индексов, тем дольше автовакуум, тем больше нагрузка на
фоновые процессы и тем дольше таблица остаётся раздутой.

### Необходимость обновления индексов

Индекс — это **производная структура**, которая обязана оставаться согласованной с
таблицей в любой момент времени. Каждое изменение данных синхронно распространяется
на все индексы, и всё это дополнительно журналируется в WAL. Отсюда — рост объёма WAL,
нагрузки на репликацию и времени восстановления после сбоя.

### Влияние на скорость записи

Итог по измерениям: **6 индексов ≈ в 4.5 раза медленнее запись**. Зависимость близка
к линейной по числу индексов, поэтому база с 15 индексами на «горячей» таблице
может писать на порядок медленнее, чем нужно, — и «лечится» это не железом, а
удалением лишних индексов.

Для OLTP-сервиса вроде нашего это критично: `bookings` — таблица с интенсивной вставкой,
и каждый лишний индекс напрямую бьёт по времени ответа `POST /api/bookings`.

### Реальное использование запросами

Самый прямой аргумент. Найдено измерениями:

- **`ix_bookings_id` — полный дубликат `bookings_pkey`**: 21 MB, `idx_scan = 0`,
  но обновляется при каждой вставке. Такие же дубликаты обнаружены ещё у четырёх таблиц —
  все они порождены директивой `index=True` на колонке с `primary_key=True`.
- **`idx_orders_status` — вырожденный индекс**: формально используется (`idx_scan = 21`),
  но `idx_tup_read / idx_scan ≈ 285 844` записи за скан, и `Heap Blocks: exact=10827`
  показывает, что таблица всё равно читается целиком. Пользы ноль, стоимость записи есть.
- **`i1`…`i6`** на тестовой таблице: 58 MB при `idx_scan = 0`.

Вывод: индекс приносит пользу, только если его действительно выбирает планировщик
**и** при этом он сокращает объём чтения. Оба условия проверяются лишь измерением.

### Итог

Индекс — это **осознанный размен**: быстрее чтение по конкретному шаблону запроса
в обмен на место, память и скорость записи. Массовое индексирование «на всякий случай»
даёт худшее из двух миров:

- запись замедляется в разы (**4.55×** на шести индексах);
- место расходуется втрое против самих данных (**291.9%**);
- кэш забивается ненужными страницами, вытесняя полезные;
- автовакуум работает дольше;
- **чтение при этом не ускоряется**, потому что планировщик всё равно выберет один
  индекс на запрос — и не факт, что созданный «про запас».

Правильный подход — тот, что применён в части 2 этой работы:
взять реальные запросы из логов → измерить `EXPLAIN ANALYZE` → найти узкое место →
подобрать **минимальный набор** составных индексов под конкретные шаблоны →
**удалить дубликаты и левые префиксы** → измерить повторно.

Результат по `bookings` показателен: индексов стало **меньше** (6 → 5), а самый
проблемный запрос ускорился **втрое** (97.6 → 32.9 мс) — потому что важно не количество
индексов, а их соответствие реальным запросам.

## Общие выводы

1. **Индекс ускоряет запрос только при высокой селективности условия.** Измеренная шкала:
   1 строка → `Index Scan` (0.05 мс); 0.14% → `Bitmap` (3.2 мс); 25% → вырожденный
   `Bitmap`, читающий всю таблицу; 50% → `Seq Scan`. Порог отказа от индекса —
   примерно 5–20% таблицы.

2. **Наличие индекса ничего не гарантирует.** Планировщик сравнивает стоимости и вправе
   его отвергнуть (`status <> 'NEW'` → `Seq Scan`). Ещё коварнее случай, когда индекс
   формально используется, но читается целиком: `(created_at, user_id)` вместо
   `(user_id, created_at)` дал **в 109 раз** худший результат при внешне «правильном» плане.

3. **Порядок колонок в составном индексе решает всё.** Формула, подтверждённая измерениями:
   **(равенства по убыванию селективности, затем диапазон/сортировка)**.

4. **Один составной индекс может заменить несколько одиночных** и заодно снять `Sort`.
   `BitmapAnd` по двум одиночным — 15.886 мс, один составной — 1.383 мс (**в 11.5 раза**).

5. **`Sort` в плане при наличии `LIMIT` — почти всегда дефект.** Сортировка обязана
   собрать все строки до выдачи первой; упорядоченный индекс останавливается на N-й.

6. **Функция над колонкой убивает обычный индекс.** `LOWER(email)` → `Seq Scan` 204 мс;
   индекс по выражению → 0.039 мс (**в 5237 раз**).

7. **Индексы дороги при записи.** 6 индексов = запись в 4.55 раза медленнее, место
   втрое больше данных. `UPDATE` замедляется даже для колонок, не входящих ни в один
   индекс, — из-за MVCC.

8. **Оптимизация — это цикл измерений, а не создание индексов.** В части 2 бóльшую пользу
   принесло не добавление, а **удаление**: дубликат первичного ключа на 21 MB и два
   избыточных левых префикса. Индексов стало меньше, а сервис — быстрее.

9. **Проблемы масштабирования не видны на маленьких данных.** Query 3 на 40 бронированиях
   не показал разницы; на 20 014 бронированиях того же пользователя — **в 26 раз**
   быстрее и в 47 раз меньше чтений. Именно поэтому scaling entity надо оптимизировать
   заранее.
